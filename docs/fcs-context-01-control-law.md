## 1. 설계 흐름 개요

공력 데이터 + 추진 + 대기모델로 6DOF 모델 구축 → 항법장치(각속도·가속도·위치 센서) 상태값 기반으로 조종면/러더/스로틀 명령 생성. 설계 순서:

1. **트림 및 선형해석** — 트림점별 조종입력·상태변수 타당성 확인, 안정성 분석
2. **SCAS** — 자세(피치/롤/요) 안정화
3. **오토파일럿** — 속도/고도/헤딩 제어
4. **유도** — 미션플래너가 생성한 임무프로파일의 경로 추종, 모드별 유도
5. **비선형 시뮬레이션 검증**

## 2. 기체 / 플랜트

### 2.1 형상
**[확정]** 델타윙, 쌍발 엔진. 조종면: 엘레베이터(엘레본) × 4, 러더 × 1. 요축 보조: 차동 추력.

### 2.2 엘레본 믹싱 (Elevon Mixing · Control Allocation)
- 4개 엘레본: 피치 = 동시(collective), 롤 = 차동(differential)
- 면이 4개 → 여유자유도 존재. **[기본값]** 내측/외측 쌍 고정 믹싱 행렬, 최적화 기반 할당은 추후 확장
- **[TBD]** 4면 배치(내측/외측 쌍 여부), 믹싱 비율, 타면각·rate 한계

### 2.3 공력 데이터베이스
- **[확정]** CFD 기반. 축: Mach, α, β, 타면각, 고도. 정미계수 + 동미계수 포함, 사실상 전체 정보 보유
- **[확정]** α 범위: 트림 조건(속도·중량)에 따라 다르며 25°를 넘는 케이스도 존재
- **[확정]** 스톨 취급 방침: DB는 기본 충실도로 사용 (고α 박리영역의 CFD 예측 불확실성 인정). 실속은 DB 비선형성에 암묵적으로 맡기지 않고 **명시적 실속 경계 테이블**(α_stall = f(Mach, 형상조건 등))을 별도 데이터로 정의
- **[확정]** 실속 경계 정본은 **공력팀 제공** — 공력팀이 CL–α 곡선 분석으로 실속각을 식별·보정하는 것이 정상 업무 분장. 툴의 DB 추출 기능은 교차확인용 (구현 문서 §데이터 참조)
- 이 단일 경계 정의를 실속 마진 감시, 엔벨로프 표시, α 리미터(§3.6)가 공유한다

- **[TBD]** 작동기 특성(대역폭, rate/position limit) — 미보유 시 **[기본값]** 2차계 가정값으로 시작, 파라미터화

### 2.5 환경 / 센서·항법
- **[확정]** 지구모델 WGS-84, 표준대기(ISA). 바람/난류(Dryden), 파고·전파고도계 노이즈는 추후 확장
- **[확정]** 저고도 임무 기준 고도: 해수면 0 ft (MSL)
- **[확정]** 항법: 툴은 EKF를 구현하지 않고, 실제 항법 출력의 통계적 특성을 재현하는 **등가 오차 모델**(잡음+바이어스+지연)을 사용한다. 제어법칙은 이 항법 출력을 피드백으로 사용하며, 항법 오차에 대한 강건성을 이 모델로 평가한다. 상세는 구현 문서 §3.1
- **[기본값]** 초기 오차 수치는 GPS/INS 통합항법의 일반적 수준. 항법팀 자료 확보 시 대체
- **[기본값]** 위치·속도 오차는 **수평(N·E)과 수직(D)을 분리**한다 — GNSS는 수신기 아래쪽 위성이 없어 수직 기하가 나쁘고(VDOP > HDOP), 기압고도 보정도 별도 드리프트원을 갖는다. 등방(3축 동일) 가정은 수직 채널을 실제보다 후하게 모사해 **저고도 임무의 고도 마진을 낙관적으로** 보이게 한다(오토파일럿 고도 루프가 `nav.pos_n[2]`·`nav.vel_n[2]`를 직접 소비). 수직 기본값은 수평 × 1.5(VDOP/HDOP 통상비)로 둔 **파생 자리표시자이며 실측 자료가 아니다** — 특히 기압고도 드리프트는 이 비율로 대표되지 않으므로 항법팀 수치 확보 시 최우선 대체 대상 [TBD]
- **[설계 유의]** 항법 갱신주기가 제어주기보다 낮을 수 있음 → 제어법칙은 멀티레이트 입력을 전제로 설계

## 3. 제어법칙 아키텍처

계층 구조 (**[확정]** 고정 아키텍처 — 자유 배선 없음):

```
미션플래너 (웨이포인트 → 임무프로파일)
  └─ 유도 (모드별: 이륙/디센트/고도유지/임무수행 + 경로추종)
       └─ 오토파일럿 (속도/고도/헤딩 명령 → 자세 명령, 주로 PI)
            └─ SCAS (자세 안정화: 피치/롤/요, PI)
                 └─ 엘레본 믹싱(제어 할당) + 차동추력 보상
                      └─ 엘레본×4, 러더, 스로틀×2
```

### 3.1 SCAS
- 피치/롤/요 자세 안정화, PI 제어 기반
- 선회 시 러더 PI 제어 + 지속 선회 유지를 위한 **워시아웃 필터**
- **[TBD]** 워시아웃 시정수 결정법, 피드백 구조 상세(각속도만 vs 자세 포함), 안티와인드업 방식

### 3.2 오토파일럿
- 속도 / 고도 / 헤딩(기수) 제어, 주로 PI
- 요축: 러더 명령 + 차동추력 스로틀 출력 보상
- **[기본값]** 속도/고도/헤딩 명령 경로에 1차 명령필터 — 급격한 명령으로 인한 타면 포화·과도 하중 방지. 시정수는 **[TBD]**

### 3.3 유도
- **[확정]** 웨이포인트 열로부터 경로 생성 → 경로 추종
- 출력: 속도/고도/헤딩 명령
- **[TBD]** 경로추종 알고리즘(LOS/L1/벡터필드), 웨이포인트 전환 조건, 모드 전환 로직

#### 3.3.1 비행 모드 목록

**[확정]** 체계 유형: **왕복 운행 비행체** (이륙~착륙). 모드는 이륙→착륙의 비행단계(phase) 순으로 구성되며, 각 모드가 오토파일럿에 넘길 명령(속도/고도/헤딩 활성화·유지 방식)을 정의한다.

| 단계 | 모드 | 설명 |
|---|---|---|
| 이륙 | 이륙 (Takeoff) | 활주로 이륙, 초기 가속·상승 |
| 상승 | 상승 (Climb) | 순항 고도까지 상승 (상승률/피치 제한) |
| 임무 | 순항 (Cruise) | 속도+고도+헤딩 동시 유지 |
| 임무 | 고도유지 (Altitude Hold) | 지정 고도 유지 |
| 임무 | 디센트 (Descent) | 임무 고도로 하강 |
| 임무 | 임무수행 (Mission) | 지정 임무 구간 저고도 비행 (기준 MSL 0 ft, §2.5) |
| 임무 | 웨이포인트 항법 (Waypoint Nav) | 경로 자동 추종 (경로추종 알고리즘 적용) |
| 착륙 | 착륙 (Landing) | 기지 복귀 후 최종 접근·착륙 |

- **[기본값]** 위 목록으로 시작. 임무 요구에 따라 가감 — RTL·로이터 등 회수형 모드는 착륙 단계 재진입으로 표현 가능
- **[설계 유의]** 델타윙은 유도항력이 커 선회 시 속도·고도 손실이 두드러짐 → 선회 시 **엘리베이터/스로틀 피드포워드 보상**으로 고도 강하 방지 (일반 고정익보다 중요). SCAS/오토파일럿 협조 항목
- **[TBD]** 각 모드의 진입·이탈(전환) 조건, 모드 간 우선순위, 비상 처리
- **[확정]** 모드 전환 로직은 **선언적 모드 테이블 + 실행기(sequencer)** 로 구현. Stateflow식 시각적 상태머신 도구는 불필요·미사용
  - 근거: 비행단계가 대부분 순차 진행이고 분기가 단순 → 각 모드가 {진입조건, 활성 명령, 이탈조건}을 갖는 테이블로 충분. 다이어그램 대비 가독성·버전관리(diff)·웹 UI 편집 모두 유리
  - 단, 전환 순간의 **범프리스 처리**(적분기 초기화, 명령 페이딩)는 별도 제어법칙 설계 항목으로 남음 (§3.4 참조)
- **[범위 註]** 임무수행 단계의 상세 임무 로직(예: 탐지·정찰 등)은 본 컨텍스트의 아키텍처·분류 범위를 벗어나며, 별도 설계 단계에서 다룬다

### 3.4 게인 스케줄링
- **[확정]** 스케줄 변수: **Mach, 고도, 연료량** — 조건 조합의 트림점에서 설계
- **[확정]** 스케줄 검증 요구: 설계점뿐 아니라 **설계점 사이 보간 구간**의 안정성 확인 — 중간점에서 보간 게인 + 해당 조건 선형모델로 마진 재계산(마진 맵 기능 재사용, §4.2). 게인 테이블 불연속 검출 포함
- **[기본값]** 스케줄 변수 처리: 유효범위 밖 외삽 금지(경계값 고정), 스케줄 변수 입력 필터링으로 게인 채터링 방지
- **[확정]** **스케줄 대상은 게인 자리 단위로 고른다.** 어떤 게인에 테이블을 붙일지는 값 편집과 다른 층의 설계 결정이며 구조를 바꾼다 — 스케줄한 자리는 탑재 코드에 룩업 + 스케줄 변수 필터 상태가 생기고, 뺀 자리는 설계점 상수로 접혀 룩업이 사라진다(형상 지문도 함께 바뀐다). 전 자리를 빼면 게인 스케줄 서브시스템 자체가 없는 형상이다
  - 자리는 **6그룹 × 3키 = 18이 아니라 16**이다: SCAS `pitch·roll·yaw` + 오토파일럿 `speed·alt·heading` × `kp·ki·k_rate` 중, **속도·헤딩 축은 rate 입력이 없어 `k_rate` 스케줄이 구조상 불가**하다(그 축은 PI만 있다). `alt.k_rate`는 유효하며 승강률 댐핑 `k_hdot` 자리다
  - [기본값] 기본 스케줄 대상은 **피치·롤의 kp·ki·k_rate 6자리** — 요축과 오토파일럿 게인은 설계점 고정. 데모의 동압 스케일이 그 6개에만 적용된다는 뜻이고, 요축 비대칭·AP 스케줄 여부는 실기체 튜닝 시 재검토 [TBD]
  - 자리 목록의 정본은 엔진 구조 정의 한 곳(`fcl/graphs.py` SCHEDULABLE)이며 조립 검증·웹 목록이 모두 이를 읽는다 — 목록을 여러 곳에 적으면 "켤 수 있다"고 보여 준 자리가 실행 시점에 터진다
- **[기본값]** 설계점 격자·검증점 밀도 — M17 자동 설계 루프의 1차 확정값 (종전 [TBD]): coarse 격자는 엔벨로프에서 유도(행(alt, fuel)별 mach 하한 = V_S(n=1, V-n 실속 경계 역보간)×1.1 실속 여유, 상한 = min(M_NO, 공력 DB 유효 상한, 실속표 축 상한) — 비직사각 허용), adaptive 트림점 삽입 기준은 **인접점 플랜트 거리** d_total > 0.25 (트림해 기울기/CONTINUITY_STEP·단주기/더치롤 wn·ζ 변화·조종효과 B 핵심 성분 상대 변화의 최대 — `design/linmodels.model_distance` 정본, 우선순위 큐 이분법이라 예산 내 언제 끊어도 최악 구간부터 세분화됨), 검증점은 breakpoint 이상 역할 인접쌍 **중점 1개/구간**. 모드/게인 전환 시 범프리스 처리는 [TBD] 유지
- **[확정]** 게인 스케줄 **다항 런타임 채택** (사용자 결정 — 종전 "실주입 [백로그]"의 해소이자 확장): 튜닝된 게인 surface를 구간별 2~4차 다항으로 적합(차수 에스컬레이션 — 허용치 만족 최저 차수, greedy knot, **경계 C0는 제약 최소제곱으로 구성 보장** — 게인 불연속 봉쇄, 기울기 점프는 정량 보고)하고, 그 다항식이 설계 표현이자 **런타임 표현**이다: M3 `PolyTable`(u-영역 호너, 외삽 clip) → M7 `PolyBlock` → 탑재 C `claw_polyeval1d`(Python↔C 비트 일치 패리티). 자리별로 Table(격자 보간)과 다항 중 택일 — 선택이 곧 형상. **v1 한정**: 다항 런타임은 1D 축 전용(2축+ 변동은 지배 축 적합 + 교차축 잔차 정직 보고), 다차원 다항·웹 스토어 경유 다항 채택은 [백로그] (웹 "게인 확정" 버튼은 보간오차 허용치 내 재샘플 테이블을 주입하고, 다항 정본은 결과 JSON `gain_export.tables`로 API 직접 주입)
  - **[확정]** **확정이 주입하는 형상은 검증한 형상이 아니다 — 그 차이를 수치로 낸다.** 그 버튼이 스토어에 넣는 것은 `gain_export.tables_resampled`, 즉 다항을 선형 격자로 **재양자화한 근사**(`resample_to_table`, `tol_interp` 0.01 [기본값])이고 세션이 검증한(margin_out) 형상은 다항 정본이다 — 차이를 어디에도 안 적으면 "확정"이 검증 결과를 그대로 물려받는 것처럼 보인다. 그래서 서버가 실제로 쓴 허용치(`resample_tol`)와 **자리별 실측 어긋남**(`resample_error` = {max_abs, max_frac, at, n_points})을 함께 내려준다. 허용치를 베껴 적은 값이 아니라 **knot 구간을 401점으로 훑어 PolyTable과 재샘플 Table을 직접 비교**한 값이다 — 다시 재는 이유는 `tol_interp`가 **목표치이지 보장이 아니기** 때문이다(구간 중점만 보며 이분하고 max_pts·depth 상한에서 멈추므로, 최악점이 중점이 아니거나 상한에 먼저 걸리면 허용치를 넘은 채 끝난다). `max_frac`은 곡선 진폭(구간 내 최대 |값|) 대비라 허용치와 **같은 자**이고, 절대값을 함께 내는 것은 게인 자리마다 크기가 달라 비율만으로 감이 안 오기 때문이다. 비다항(격자) 자리는 재샘플이 곧 원본이라 0.0을 **명시적으로** 채운다 — 키가 비어 "미측정"과 "무오차"가 섞이지 않게. 허용치도 명시 전달해 엔진 기본값이 바뀌어도 보고한 값과 실제로 쓴 값이 갈리지 않는다. 화면 표기는 아직 붙지 않았다(값은 결과 JSON에 실린다)
- **[기본값]** 게인 테이블 **근사식 피팅**(웹 수동 탐색·표시 전용으로 존치): 구간별 최소제곱 다항식 회귀(차수 1~6, 센터·스케일 정규화) — 자동 경로의 적합 정본은 엔진 `design/fit.py`이고 웹 `lib/polyfit.js`는 수동 실험·오버레이 표시용이다 (역할 분리 명시)

### 4.2 선형화 / 안정성 해석
- **[확정]** 트림점별 구간 선형화 (수치섭동 상정)
- 횡축(lateral-directional) / 종축(longitudinal) 분리 해석
- **[기본값]** 작동기·지연 포함: 마진 계산용 선형모델에는 작동기 동특성(§2.4 가정값)과 주요 지연(항법 출력·제어주기)을 포함하는 것을 기본으로 한다 — 작동기·지연 제외 마진은 낙관적. 포함/미포함 선택 옵션으로 영향 분리 분석 지원. **구현됨(M9 증분)**: 작동기는 실제 2차계(§2.4 SecondOrderActuator, wn·ζ) 자체를 개루프에 캐스케이드 — 새 지연 모델이 아니라 기존 모델 재사용(레이트/위치 한계는 비선형이라 소신호 해석 제외). 지연(항법 출력+제어주기, 작동기와 무관한 별도 출처)은 순수 전송지연이라 유한차원 상태공간 불가 → Padé 근사 캐스케이드. 실측(데모 M0.6 피치레이트 루프): 작동기·지연 미포함 PM 91.0° → 포함 시 PM −76.3°(불안정 전환 — 개루프 크로스오버 52 rad/s가 작동기 대역폭 30 rad/s 초과)로, "제외 마진은 낙관적" 경고가 실증됨
- **[기본값]** 지연의 선형 표현: Padé 근사 차수 2 (마진 해석 통상 차수). 기본 총 지연 0.035 s = 항법 출력 지연 0.03 s(§2.5 [기본값]) + 제어주기(100 Hz) 등가지연 0.005 s. 포함 범위는 항법·제어주기만(센서·통신 등 추가 지연원은 데이터 확보 시 확장) — 엔진 API는 포함/미포함 모두 요청이 명시(중립), 웹 폼 기본값만 포함 ON
- **[기본값]** 평가지표: 고유치·감쇠비(단주기, 장주기, 더치롤, 롤, 스파이럴), 이득·위상여유. 필요 시 MIL-F-8785C류 비행성 기준 추가
- **[확정]** **마진 맵**: 이득·위상여유를 Mach-고도-연료 격자 전체에 대해 계산, 비행영역 내 마진 취약 구간 식별. 100 vs 50 Hz 마진 변화 비교도 동일 기능으로 수행

  - **[확정]** **롤 모드는 참여도로 지목한다** — 판정선(§5 "롤 대역폭(λ) 판정선")을 붙이려고 λ를 들여다보니 **지표 자체가 롤을 안 재고 있었다**. 종전 `roll_lambda = max|Re| over 실근` 휴리스틱은 두 군데서 깨진다. ① 요 댐퍼가 만든 실근이 롤 근보다 빠르면 그쪽이 뽑힌다 — 데모 M0.6/h1000에서 롤 게인을 **0으로 완전히 꺼도 λ가 6.45**다(재려는 게인에 거의 반응하지 않는 지표였다). ② 댐퍼가 약해지면 롤 모드가 더치롤·나선과 합쳐져 **실근으로 존재하지 않는다** — 같은 점 ×0.2에서 남은 실근의 p 참여도는 0.080으로 어느 쪽도 롤이 아니다. 실측(롤 게인 배수 → 종전 `max|Re|` / 참여도로 지목한 λ / 참여도): ×1.0 → 16.5945 / 16.5945 / 1.002, ×0.5 → 8.8227 / 8.8227 / 0.932, ×0.2 → 6.5779 / 6.5779 / **0.080**, ×0.05 → 6.4691 / **0.3463** / 0.238, ×0 → 6.4510 / **2.2447** / 0.663. 해법: `closure.roll_real_mode`가 표준 participation factor `|V[p,k]·V⁻¹[k,p]|`(모드별 상태 합이 1)로 **롤 상태 p를 가장 많이 담은 실근**을 지목하고 λ와 참여도를 함께 낸다(`lat_metrics` → `roll_lambda`·`roll_unstable`·`roll_participation`). 참여도가 `lam_part_min`(0.5 [기본값]) 미만이면 판정은 **na** — 통과도 실패도 아니고 "롤 대역폭을 잰 게 아니다"가 정직한 답이다(위 ×0.2·×0.05가 그 경우이고, ×0은 참여도 0.663의 깨끗한 fail — λ 2.24는 목표 12의 0.187배다). 지표 계산과 판정은 분리한다 — `closure`는 셋을 내기만 하고 문턱은 `criteria.judge_bandwidth`가 안다(§5). p 자리는 `x_names`에서 **이름으로** 찾는다: 상태 순서를 여기 손으로 다시 적으면 `trim.linearize.LAT_STATES` 정본과 갈린다. **같은 "빠른 실근 = 롤" 휴리스틱이 `analysis/modes.classify_lat`에는 그대로 남아 있다** — 이번 변경은 자동 설계 경로(`closure`)만 고쳤다(§7 백로그)

- **[확정]** **마진 부족 원인 분류 6-verdict** (M17 `design/classify.py` — 부족 시 처방이 원인별로 다르다): ⓪ gain_sign_flip — 실효 게인 부호가 설계와 반대(적합 링잉이 0을 가로지름) → 승격으로는 안 풀리므로 그 점을 고정한 재적합(refit_at) ① structural_limit — 자유 게인 국소 최적으로도 미달 → **에스컬레이션 보고 전용**(필터·작동기 대역폭·지연 예산 등 상위 설계 변경은 자동 적용 금지, 교차/작동기 비·지연 위상 기여를 근거로 동봉). 근거에 **완화 프로브**를 함께 낸다 [확정]: 지연을 0으로·작동기 대역폭을 3배로 각각 **하나씩만** 바꿔 재튜닝해 어느 예산이 병목인지 실측 지목한다 — 자동 적용은 안 해도 "무엇을 바꾸면 통과하는가"까지는 기계가 답해야 사람이 판단할 수 있고, 종전 두 수치(ωc/작동기 비·지연 위상)는 둘 다 ωc에 비례해 함께 커지므로 병목을 가려내 주지 못했다. 데모 M0.75/h0/f200(해수면 순항 한계)이 이 경로로 §7 백로그 "작동기 대역폭 요구 사양 미도출"을 재발견했다 ② plant_variation — 인접 앵커 플랜트 거리 > 0.25(리파인 tol과 **동일 상수** — 기준 이원화 금지) → 검증점을 트림·선형화점으로 승격 ③ gain_interp_valley — 최적은 통과 ∧ 보간 게인 괴리 > 10% ∧ 이웃 breakpoint 통과 → 검증점을 breakpoint로 승격 + 최적 게인 채택 + 재적합 ③′ **fit_residual** — 같은 괴리가 **앵커**에서 나면 격자가 성긴 게 아니라 적합이 그 점을 못 지나간 것이다 [확정]: TUNE이 매 이터레이션 그 점의 자유 게인 최적을 샘플에 넣고 병합에서 튜닝 샘플이 이기므로(`_stage_fit` setdefault — 낡은 승격 값이 최신 결과를 덮는 것을 막는 의도적 가드), "그 점의 최적 게인을 샘플에 고정"하는 종전 처방(refit_at)은 **구조적 no-op**이면서 applied로 기록돼 이터를 태웠다. action=**tighten_fit** — 적합 허용치 ×0.5·구간 수 +1로 조이는 방향으로만 움직이는 단조 래칫에 상한 3회라 종료가 보장된다. breakpoint는 TUNE이 안 도는 자리라 주입이 실제로 값을 바꾸므로 종전대로 refit_at을 유지하고, 주입 게인은 출처를 나눠 refit_gains가 promoted_gains를 덮되 튜닝 샘플에는 여전히 진다(한 겹 setdefault이던 동안에는 같은 점이 다시 실패해도 처음 들어간 승격 값이 계속 이겨 새 처방이 아무것도 안 바꿨다) ④ simple_deficit — 나머지 → 검증점 추가. ②③ 동시 성립이면 상위 집합 처방(②)
  - **[확정]** **분류의 단위도 자리다** — structural_limit 판정과 완화 프로브의 "해소" 판정 모두 튜너의 **자리 단위** status를 쓴다(점 단위는 evidence에 참고로만 남긴다). 점 단위로 재면 피치가 안 되는 점의 롤 실패까지 structural_limit → escalate(적용 버튼 없음)로 둔갑해 원래 나왔어야 할 breakpoint 승격이 사라진다 — 고칠 수 있는 것을 못 고치게 만드는 결함이라 "전 운영점을 합격선에 넣는다"는 1차 목표의 직접 손실이다. 완화 프로브도 같은 이유로 자리 단위다: 점 단위로 재면 이 자리를 고친 완화조차 다른 축이 못 따라오면 "여전히 미달"이 되어 화면의 결론 문장이 거짓이 된다
  - **[확정]** **분류기의 자유 게인 최적은 손설계 정본(design_base)에서 브래킷을 잡는다** — `tune_point`은 설계값에서 **부호와 탐색 브래킷**(4×|k_design|)만 읽으므로, 오케스트레이터가 넘기던 실효 설계값(`{**손설계, **적합 상수}`)을 쓰면 적합이 접은 값이 곧 탐색의 출발점이 되어 "게인으로 될 일인가"에 틀린 답이 나오고 그 g_opt가 valley 괴리 계산과 승격 게인에 그대로 들어간다. 보간 게인 비교(`scheduled_gains`)에는 실효값이 그대로 필요하므로 **둘 다** 넘긴다. 크기 차이는 위 브래킷 확장이 흡수하지만(적합이 −0.05로 접어도 256배까지 넓혀 같은 최적 −0.592·λ 12.00을 찾는다) **적합 상수가 0인 자리는 못 산다** — 4×0 = 0이라 방향 정보가 없어 튜너가 통째로 건너뛰고(zero_design) 0.0을 "자유 게인 최적"이라 낸다. 부호도 같은 자리에서 오며, 뒤집힌 부호는 확장이 고칠 수 있는 종류가 아니다
- **[확정]** **엔벨로프 경계 점의 취급** — 트림은 수렴했으나 포화·α 여유 미달인 점(`trimmable=False`, 격자·리파인이 세우는 엔벨로프 실경계 플래그)은 스케줄 인지 검증에서 **마진을 내되 실패 목록·판정 수에서 제외**한다(`schedmap` case의 `outside_envelope`, 보고에는 개수로 남긴다 — 조용한 누락 금지). 근거: 자동 튜닝이 이미 이 점을 건너뛰므로(`tune_points` skipped) 스케줄은 그 조건을 덮으라고 요구받은 적이 없는데, 채점만 하면 **반영해도 듣지 않는 처방**이 나온다 — 앵커로 승격해도 TUNE이 다시 건너뛰어 게인 샘플이 늘지 않는다. 마진 수치 자체는 남긴다(왜 거기가 경계인지의 자료). 트림 미수렴(판정 자체 불가, loops 비움)과는 다른 상태로 구분한다
- **[확정]** **이터레이션 자동화** (M17 `design/orchestrator.py`): COARSE→REFINE→TUNE→FIT→VERIFY→CLASSIFY 상태 머신이 처방을 반영하며 순환. 기본은 **승인 게이트(gated)** — 분류 후 일시정지, 승인된 처방만 반영해 재개(전자동은 옵션, 에스컬레이션은 어느 모드든 보고만). 종료 3겹: 점 예산 + 역할 승격 단방향 래칫 + 이터레이션 상한. 수렴 판정: 전 점 통과 ∨ 잔여 실패 전부 에스컬레이션 ∨ 예산 소진
  - **[확정]** **처방 효과 검증** — apply 시점에 그 (점, 자리)의 판정·부족 비율을 찍어 두고 다음 VERIFY가 after를 채워 실제로 움직였는지 판정한다. 볼 수 없으면(전·후 중 하나가 없으면) 변화 없음이라 **단정하지 않는다** — 모르는 것을 무효로 세면 멀쩡한 처방이 봉인된다. 연속 2회 무효면 그 (점, 자리, verdict)를 **봉인**해 다음 CLASSIFY의 적용 대상에서 뺀다. 종전에는 "반영됨(applied)"만 찍고 결과를 안 봐서, 듣지 않는 처방이 예산 소진까지 같은 순환을 돌 수 있었다(위 ③′가 실제로 도달 가능한 경로였다). report에 `ineffective_actions`·`sealed`·`fit_tighten`을 낸다 — "처방을 냈다"와 "고쳤다"는 다르고, 화면이 그 둘을 구별할 수 있어야 한다

## 5. 검증 기준 (제어법칙 관점)

- **[기본값]** 합격기준은 일반 기준: 오버슈트, 정착시간, 정상상태 오차, 경로오차 한계. 허용오차 수치는 폐쇄망 Simulink 대조 시 확정
- **[확정]** 합격기준 수치는 파라미터 관리 계층(구현 문서 §5.5)으로 관리 — 판정 기준이 파라미터 지문에 포함되어 산출물 계보·Δ리포트에 요구도 버전이 자동 반영됨
- **[기본값]** **마진 합격기준의 엔진 이관** (M17 `design/criteria.py` — 종전 웹 색칠 로직에만 있던 판정선의 1차 이관): 합격선 PM ≥ 45°·GM ≥ 6 dB, 심각선 PM 30°, **설계 목표선 GM 8 dB**·레이트 댐퍼 폐쇄 모드 감쇠 ζ ≥ 0.30(합격)/0.50(목표). 판정 불가(nan — 교차 없음)는 fail이 아니라 na로 분리(무한 여유 오인 금지 원칙). 기준은 canonical 지문을 갖고 판정 산출물에 동봉된다 — 웹은 `/design/defaults`로 이 값을 소비(하드코딩은 폴백). 허용오차 최종 수치는 폐쇄망 검증 시 확정 [TBD 유지]
- **[확정]** **목표선과 튜닝 목표의 정합** — warn은 "합격선은 넘겼으나 **설계 목표 미달**"을 뜻하므로, 판정의 목표선(`MarginCriteria.gm_good_db`·`zeta_good`)은 튜너 목표(`TuneTargets.gm_db`·`zeta_sp`/`zeta_dr`) **이하**여야 한다. `AutoDesignConfig.__post_init__`이 이 부등식을 제출 시점에 강제한다(위반 시 422). 배경: 종전 목표선 GM 10 dB > 튜너 목표 8 dB라 **자유 게인 최적점조차 구조적으로 warn**이었고, 실행 결과가 의미 없는 경고로 뒤덮여 진짜 문제를 골라낼 수 없었다. 웹 마진 탭의 음영 문턱도 같은 수치를 쓴다(같은 GM을 두 탭이 다르게 판정하지 않는다)
- **[확정]** **부족량의 단일 정의** — 판정어(ok/warn/fail) 옆에 **얼마나**를 낸다. `MarginCriteria.shortfall`이 자리 하나의 지표별 {요구, 달성, 부족, **부족 비율**}을 내고, 어느 지표를 보는지는 자리 종류가 정한다(마진 자리 pm_deg·gm_db, 감쇠 자리 ζ류, 롤 roll_lambda). 비유한값(nan = 교차 없음)은 0이 아니라 **None**이다 — 0으로 두면 "판정 불가"와 "부족 없음"이 같은 수가 된다. 실패 정렬 키 `severity`는 그 **부족 비율의 최대값**이고 **클수록 심각**(내림차순 정렬), 잴 지표가 없는 실패는 +inf라 맨 앞이다 — "얼마나 나쁜지 모른다"를 맨 뒤로 보내면 예산이 끊길 때 가장 안 보이는 자리가 조용히 남는다. 비율로 재는 이유: PM(도)·GM(dB)·ζ(무차원)·λ(rad/s)는 단위가 달라 절대값으로 한 줄에 못 세운다. 종전 절대 축(PM은 도 그대로, ζ는 ×90)은 그 ×90 환산이 감쇠 부족을 과대평가해 **순서를 뒤집었다** — PM 35°(요구선 45° 대비 22% 부족, 축에서 35.0)가 ζ 0.28(0.30 대비 6.7% 부족, 축에서 25.2)보다 **덜 심각하게** 정렬됐다. 이 정렬이 곧 분류기의 작업 목록 순서라, 예산이 끊기면 더 급한 자리가 남는다. 부족 레코드는 마진맵 실패 목록과 분류기 evidence에 **전 verdict 공통**으로 실린다(종전엔 계산해 놓고 버려져 화면이 "현재 PM 38.2°"만 말하고 요구선 45°도 부족 −6.8°도 못 냈다)
- **[기본값]** **롤 대역폭(λ) 판정선은 목표 대비 비율** — λ는 안정성 마진이 아니라 조종성 성능 지표라 관례적 **절대** 합격선이 없고, 요구 자체가 그 실행의 튜닝 목표(`TuneTargets.roll_lambda`)에서 온다. 그래서 비율로 잰다: `lam_min_frac` 0.5(합격) / `lam_good_frac` 0.8(목표), 그 사이는 warn. 폐쇄망 검증에서 확정할 자리다(§7 "합격기준 허용오차 수치"와 한 세트). `judge_bandwidth`에 `unstable` 인자가 있는 이유: λ = max|Re|는 **부호를 지우므로** 발산근 +12 rad/s가 "목표 12 달성"으로 보인다 — 수치와 무관하게 fail이어야 하고, 튜너 쪽은 댐퍼 안정 캡이 걸러 주지만 검증 쪽에는 그 게이트가 없어 이 인자가 유일한 방어다. 판정선을 세운 변경은 **검증 경로 배선을 일부러 분리했다** — `schedmap`의 roll_rate를 종전 상수 "ok"(정보 보고)에서 이 판정으로 바꾸면 실패 수 자체가 달라지므로 단독 변경으로 뗀 것이다(그 전까지 이 자리는 **절대 실패할 수 없는 판정**이라 judged 수만 채웠다). 비율 수치의 최종 확정은 폐쇄망 검증 [TBD]
  - **[확정]** **그 배선이 붙었다 — roll_rate가 판정을 받는다.** `schedmap`이 roll_rate entry에 `target`(그 실행의 `TuneTargets.roll_lambda`)·`roll_unstable`·`participation`을 실어 `judge_bandwidth`로 판정한다. 검증이 튜닝과 **같은 목표**를 봐야 성립하는 판정이라 오케스트레이터가 `scheduled_margin_map`에 targets를 넘긴다. 데모 손설계 스케줄에서 M0.2/h0 두 점이 목표의 0.68~0.72배로 **warn**이 된다(종전에는 ok였다) — fail·에스컬레이션 증가는 없다. 분류기 쪽도 같은 결함이 있었다: 롤 자리에서 `zeta_dr`을 찾는데 롤 achieved에는 그 키가 없어 **항상 na**였다(실패해도 분류가 안 됐다) — 이제 `roll_lambda`·`target`으로 `judge_bandwidth`를 부른다. 참여도 인자도 이 경로로 받는다: λ를 잰 실근이 롤 상태를 `lam_part_min`(0.5 [기본값])만큼도 안 담았으면 **na**이고, 지목 규약과 실측은 §4.2 "롤 모드는 참여도로 지목한다"가 정본이다. 참여도 문턱의 최종 확정도 비율 수치와 한 세트 [TBD]
- **[확정]** **판정선의 단일 정본은 `GET /api/design/defaults`다** — 이 엔드포인트가 criteria(엔진 `MarginCriteria` 기본값)와 **사유 코드 문구**(`reason_text` = 엔진 `tune.REASON_TEXT` 그대로)를 함께 내려주고, 웹 **마진 탭과 설계 탭이 그 하나를 쓴다**. 종전에는 `views/margins.js`가 *"하드코딩은 폴백 — 정본은 /design/defaults"*라 적어 놓고 **그 엔드포인트를 부르지 않았고**(`lib/plot.js`도 PM 30/45를 하드코딩했다), 그래서 `pm_min_deg`를 50으로 올리면 마진 탭은 47° 점을 **초록**으로, 설계 탭은 **fail**로 칠했다 — 같은 수를 두 탭이 다르게 판정하는 상태다. 이제 문턱을 인자로 받고 마진 탭이 실제로 fetch하며, **폴백을 쓴 경우 그 사실과 사유를 화면에 적는다**(화면이 자기 기준을 몰래 쓰지 않게). 사유 문구가 같은 편에 실린 근거도 같다: 사유 코드도 그 뜻도 엔진이 정본이라 웹이 문구를 다시 적으면 갈린 쪽이 화면이 된다 — 서버 표를 우선 쓰고 폴백 맵은 뒤에 두며, **모르는 코드는 코드 그대로** 보여 조용히 사라지지 않게 한다. (구현 문서 §5.5 "중복 정의 금지"의 적용이며, 위 목표선 정합 항목이 세 자리에 한 수치를 공유시킨 것과 한 계열이다)
- **[확정]** 엔벨로프 감시 요구: 실속 마진(α_stall − α) 시계열, 임무프로파일 전체 최악 마진 요약, DB 유효범위 이탈 플래그(실속 판정과 별개)
- **[기본값]** **기준면 여유 플래그**: 고도가 기준면(기본 0 m = 해수면 MSL, §2.5) 아래로 내려가면 플래그 + 전 구간 최저 고도·시각 요약. 지형·파고 미모델이므로 **충돌 판정이 아니라 특이 상황 표시**이며 시뮬을 중단하지 않는다. 배경: 이 감시가 없던 동안 저고도 임무가 해수면 아래 수십 m를 날면서도 이탈 플래그 없이 정상 완주로 기록됐다(유일한 고도 하한이 ISA 모델 유효 하한 −4,990 m뿐이었고 이는 지면이 아니다). 특이 상황이 잦아지면 지형·파고·RALT 모델링을 재검토 [TBD]
- 스톨 충실도 한계: 실속 진입 거동은 DB 범위 내 재현 가능하나 실속 후 동적 효과(히스테리시스 등)는 정적 테이블로 재현 불가. 목적은 실속 후 거동 예측이 아니라 **실속 회피 설계·검증**
- **[확정]** 최종 검증은 기존 Simulink 모델과 대조 (보안상 설계 중 참조 불가, 완성 후 검증만 가능)
