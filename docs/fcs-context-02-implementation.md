### 2.2 제어 요소 라이브러리 (Primitive Block Set)

**[확정]** 아래 원시 요소들이 C++ 코어의 구현 범위이자, 추후 코드젠 모듈의 생성 단위가 된다. 각 요소는 레지스트리+스키마 원칙(§2.3)을 따라 웹 UI에서 자동 편집 가능해야 한다.

### 2.3 계층 구조

**[확정]** 최종 형상은 C++ 코어 + Python 해석층 하이브리드. 단, 개발 전략은 **Python 레퍼런스 우선** (모듈 문서 03 §7.1 채택):
- Phase 1~4의 코어(제어 요소·보간·환경·플랜트·법칙 실행부)는 순수 Python(NumPy/SciPy) **레퍼런스 구현**으로 완성. 코어 경계 API를 고정해 두고, 성능이 문제 되는 시점(몬테카를로·배치 규모 확대)에 pybind11 기반 C++ 구현으로 **드롭인 교체**
- Python 레퍼런스판은 폐기하지 않고 C++판의 **회귀 기준(oracle)** 으로 상시 유지 — 이중 구현이 아니라 검증 자산

| 계층 | 언어/기술 | 담당 |
|---|---|---|
| 코어 라이브러리 | C++ (선행: Python 레퍼런스) | 공력 DB 보간, 6DOF 운동방정식, 작동기, 추진, 대기모델, 적분기, 제어법칙 실행 |
| 바인딩 | pybind11 | C++ 코어의 Python 노출 |
| 해석층 | Python | 트림(scipy.optimize — SLSQP/trust-constr), 선형해석(python-control), 배치실행, 플롯·리포트 |
| 백엔드 | Python + FastAPI **[확정]** | REST API, 작업 실행(배치 트림/시뮬), 웹소켓 진행률, 결과 저장 |
| 프론트엔드 | 웹 — 바닐라 ES 모듈, no-build **[확정]** | §4 웹 UI |

- 근거: 시뮬 속도 + 추후 실시간/HIL 모듈에서 검증된 동일 C++ 코드 재사용 + 해석은 Python 생태계
- **[확정]** 실시간성 고려: 코어는 동적할당 최소화 등 실시간 친화 코딩 스타일
- **[확정 설계원칙]** **엔진 우선**: 엔진을 CLI/Python API로 먼저 완성, 웹 UI는 동일 API를 소비하는 별도 층 (UI가 엔진 개발을 막지 않도록)
- **[확정 설계원칙]** **샘플레이트 최상위 파라미터화**: 이산화 계수 하드코딩 금지, 주기(100→50 Hz 등)로부터 자동 계산. 주기 변경 시 이산 제어기 포함 위상여유 재계산 + 응답 비교 자동화 기능 제공
- **[확정 설계원칙]** **레지스트리 + 파라미터 스키마**: 교체 가능 컴포넌트(경로추종 알고리즘, 적분기, 필터 등)는 자신의 파라미터 정의(JSON 스키마)를 노출. UI는 스키마로부터 폼 자동 생성 — 새 컴포넌트 추가 시 UI 코드 수정 불필요

### 2.4 설계값 연계·정량 영향성 평가

**[확정 — 신규 요구]** 모듈 간 설계값은 유기적으로 연계되며, 어느 단계의 수치 변경이든 전체 출력에 미치는 영향을 정량 평가할 수 있어야 한다.

- **계보(lineage) 추적**: 모든 설계 산출물(트림표, 선형모델, 마진 맵, 시뮬 결과)은 자신이 계산된 파라미터 스냅샷의 **지문(fingerprint)** 을 기록한다 (§5.5 파라미터 계층이 지문 발급)
- **[확정]** 지문 대상 확장: ParamSet뿐 아니라 **입력 데이터 파일(공력 DB, 실속 경계 테이블)의 해시·버전**도 산출물 계보에 기록 — "어떤 DB 버전 + 어떤 파라미터 버전으로 계산됐는지" 재현 가능해야 Simulink 회귀 대조(§7)가 성립
- **설계 파이프라인 DAG**: params → 트림 → 선형화 → 마진 → 시뮬의 산출물 의존 그래프를 관리. 파라미터 변경 시 영향받는 산출물만 자동 무효화·증분 재계산
- **정량 Δ리포트**: 변경 전/후 두 파라미터 스냅샷에 대해 파이프라인을 재실행하고 차이를 정량 비교 — 트림점 이동, 고유치·감쇠비·이득/위상여유 변화, 응답지표(오버슈트·정착시간)·경로오차·실속마진 변화
- **파라미터 스윕/민감도**: 지정 파라미터를 격자로 흔들어 출력 민감도 산출 (배치 실행 재사용)
- 기존 100 vs 50 Hz 마진 비교(§2.3 샘플레이트 원칙)는 이 기능의 특수 사례로 흡수
- 담당: 모듈 문서(03) M15 `pipeline`

## 3. 모듈 구성

**[확정]** 현행 Simulink 서브시스템 구조를 따라 아래 6개 모듈로 구성한다.

| 모듈 | 담당 | 주요 요소 |
|---|---|---|
| 1. Flight Control | SCAS, 오토파일럿, 게인 스케줄링, 엘레본 믹싱(제어 할당) | PID, State-Space, 필터, 게인 테이블 |
| 2. Guidance | 경로 생성·추종, 비행모드 실행기 | 경로추종 알고리즘, 웨이포인트 로직, 모드 테이블 |
| 3. Navigation | 항법 상태 추정 출력 제공 | **등가 오차 모델** (§3.1) — EKF 미구현 |
| 4. Actuator | 작동기 동특성 | Transfer Function/State-Space, Rate Limiter, Dead Zone, Backlash |
| 5. Sensor | IMU/GPS 모델 | 노이즈, 지연 (초기에는 이상 센서) |
| 6. Aircraft Dynamics | 6DOF, 공력, 추진, 대기·중력·지구모델 | Lookup Table, Quaternion, 좌표변환, 적분기 |

### 3.1 항법(Navigation) 모듈 — 등가 오차 모델

**[확정]** 툴은 EKF를 구현하지 않는다. Navigation 모듈은 실제 항법(EKF) 출력의 **통계적 특성을 재현하는 등가 오차 모델**로 구현한다.

```
항법 출력 = 참값(6DOF) + 오차(백색잡음 + 상관잡음/바이어스) + 지연
```

**근거**
- 툴이 EKF를 구현해도 실제 비행할 항법팀의 EKF와는 다른 근사물 → 현실성 착시만 유발
- 등가 오차 모델은 실제 EKF의 **성능 수치**(공분산, 지연)를 그대로 반영 가능 → 재구현보다 실제에 근접
- 제어루프가 느끼는 것은 제어대역 대비 빠른 잡음과 느린 바이어스뿐이며, 추정기 내부 구조는 제어기 설계에 영향 없음
- 항법은 별도 전문 영역 — 중복 개발 회피

**인터페이스 개방**: Navigation 모듈은 교체 가능 컴포넌트(레지스트리, §2.3)로 등록하여, 추후 항법팀의 실제 EKF 모델이나 비행소프트웨어 코드를 그대로 꽂을 수 있게 한다.

**오차 모델 파라미터** (상태별로 정의)
| 항목 | 내용 |
|---|---|
| 백색잡음 | 표준편차 (위치/속도/자세/각속도별) |
| 바이어스 | 초기 바이어스 + 상관시간(1차 마르코프) |
| 지연 | 항법 출력 지연 (transport delay) |
| 갱신주기 | 항법해 출력 주기 |

**[기본값]** 초기값은 GPS/INS 통합항법의 일반적 수준으로 시작한다. 항법팀의 실측·공분산 해석 자료 확보 시 대체.
- 위치: 수 m 급 (수평/수직 구분)
- 속도: 0.1~0.5 m/s 급
- 자세(롤·피치): 0.1° 내외 / 방위: 롤·피치 대비 큼
- 지연: 수십 ms 급
- 갱신주기: 제어주기(100 Hz)와 동등하거나 낮음 → 멀티레이트 처리 필요
- **[TBD]** 구체 수치는 항법팀 자료 확보 시 확정. 위 값들은 자리표시자(placeholder)

**[확정]** 진입 UI는 **블록 다이어그램 허브** (Simulink "다이어그램에서 시작" 대응): 고정 구조 신호흐름 다이어그램(SVG — 설계 순서 ①~⑤ 중첩 점선 프레임, 게인 스케줄 점선 배선, 항법 피드백 경로 포함)이 첫 화면이고, 블록·프레임 라벨 클릭 → **서브시스템 하위 페이지**(#blocks/<id> — Simulink 서브시스템 더블클릭 대응, 브라우저 뒤로가기로 상위 복귀): 브레드크럼 + 내부 블록도(포트·합산점·이득 경로 — 엔진 구현과 1:1, 코드에 없는 구조는 그리지 않음) + 설계 노트([확정]/[기본값]/[TBD] 칩 — fcs-context 태그와 동일 의미) + 파라미터 패널. 파라미터 패널: ① 레지스트리 스키마 폼/열람 표(§2.3 폼 자동 생성 — 단위·범위·기본값, 파라미터 보유 법칙 컴포넌트 Autopilot·ScasAxis·Mixer를 레지스트리 "fcl" 카테고리에 등재) ② 정본 편집 화면 이동(게인 스케줄·SCAS→게인 탭, 미션플래너·유도·작동기·항법→시뮬 탭, α 리미터→엔벨로프 탭, 플랜트→트림 탭). 폼 편집(시뮬 주입)은 **주입 경로가 있는 블록만** 허용 — 현재 오토파일럿(전체 kwargs 교체, 시뮬 탭 '편집 AP') — 진실 이원화 방지. 캠페인 단위 작업(트림 격자·마진 맵·미션 실행)은 탭 유지.

**[확정]** 드릴다운은 **깊이 무제한(재귀)**: 하위 페이지 SVG 안의 진입 블록(`data-child`) 클릭 → 해시 세그먼트 추가(#blocks/scas/pitch/pi — Simulink 다층 더블클릭 대응). 트리는 SUBSYSTEMS children 재귀(자식은 crumb 짧은 라벨 필수, 단계 태그는 루트 상속), 브레드크럼 중간 클릭으로 임의 조상 이동. 파라미터 패널·SVG 수치 연동(data-p)은 **루트 블록 스키마 기준** — 자식 페이지에서도 동일 폼·연동 동작. 1차 페이지 범위: SCAS 층2 = 3축 서브시스템 블록 개요 → 층3 = 축별 상세(피치/롤/요 — ScasAxis 1:1) → 층4 = PI 내부(클램프 AW — 3축 공유 정의) · AP 층2 = 3채널 블록 개요 → 층3 = 채널별 상세(헤딩/고도/속도 — 명령필터·PI·클립·FF 합류·재클립). 배선·구조 정합은 테스트 가드(data-child ↔ children 양방향, data-p ⊆ 루트 스키마 — children 재귀).

담당 기능 (**[확정]** 전부 웹):
- 트림 케이스 매트릭스 정의·배치 실행·진행률 모니터링 (테이블 편집)
- 결과 대시보드: 고유치 맵, 보드선도, 감쇠비 테이블, **마진 맵**(Mach-고도-연료 격자) 인터랙티브 플롯, 트림 가능/불가·요구도 만족 여부 색상 맵(트림 판정 플래그·합격기준 판정 재사용)
- 지도 위 웨이포인트 / 임무프로파일 편집
- 시뮬레이션 재생 (엔벨로프 감시 플래그·실속 마진 시계열 포함)
- 검증 리포트 열람·공유
- 게인 스케줄 테이블 편집
- 제어법칙 파라미터/옵션 편집 + 신호흐름 다이어그램(고정 구조 표시 — 블록 클릭 허브)
- 공력 DB 뷰어 (§4.2)

운영 형태:
- **[확정]** **단독 사용자, 로컬 서버**. 다중 사용자·인증·동시 작업 큐·편집 충돌 처리 스코프 제외 (추후 확장 여지)
- 폐쇄망 이점: 서버 1대 배포로 브라우저 접속 → 개별 PC 툴체인 설치 대비 반입 유리
- **지도 타일**: 폐쇄망에서 인터넷 타일(OSM 등) 불가 → 오프라인 타일 서버 반입 또는 위경도 격자+해안선 벡터 폴백 모드를 처음부터 설계
- **[확정]** 프론트엔드 스택: **순수 바닐라 ES 모듈 + no-build, 외부 의존 0** — 근거: ① 폐쇄망 반입물 = `web/` 파일 전부, 현지 수정이 텍스트 에디터로 가능(빌드 툴체인 반입 불요) ② eval-free — 엄격 CSP(unsafe-eval 금지) 환경에서도 동작(런타임 템플릿 컴파일 프레임워크 배제 사유) ③ 반입 심사 가능한 비-미니파이드 소스. 플롯은 자체 Canvas — uPlot 등 단일 파일 vendored 반입은 필요 시 백로그. 서버(FastAPI StaticFiles)가 정적 서빙 — 서버 1대 = 배포 전체
- **[기본값]** 웹 테스트 전략: 로직 모듈은 공존 `*.test.js`를 node 내장 러너(`node --test`, npm 의존 0)로 — **개발 환경 전용 도구**(반입물 아님). DOM 조립 전용 모듈은 얇게 유지하고 실서버 데모로 검증

- 용도: DB 임포트 시 데이터 이상 검사, 공력팀 제공 실속 경계값과의 교차확인

- **[TBD]** 게인·설계 데이터 형상관리 방식 (git 사용 제안)

### 5.5 파라미터 관리 계층 (Data Dictionary 대체)

**[확정]** Simulink Data Dictionary가 담당하던 변수 관리를 대체하는 계층을 둔다.

- 관리 대상 예: 제어 게인(Kp, Ki 등), 기하(WingArea, CG), 질량·관성(Mass, Ix, Iy, Iz), 작동기·엔진 파라미터, 리미터 값, 검증 합격기준 수치(오버슈트·정착시간·경로오차 허용치 등 — 도메인 문서 §5)
- 요구사항:
  - 단일 정의 원본에서 C++ 코어 / Python 해석층 / 웹 UI가 모두 참조 (중복 정의 금지)
  - 단위·설명·유효범위를 메타데이터로 보유 → 웹 UI 폼 자동 생성 및 입력 검증에 활용
  - 연료 소모에 따른 질량·CG·관성 변화는 시간·상태 의존 파라미터로 취급
  - 텍스트 기반 파일로 저장하여 버전관리(diff) 가능
- **[확정]** "중복 정의 금지"의 집행 규칙 — **웹은 엔진 기본값을 재기술하지 않는다**: 요청에 사용자가 실제로 정한 값만 싣고 나머지는 엔진 ParamDef가 채우게 한다(부분 지정 보충). 화면에 즉시 값을 보여야 해서 폴백 사본이 불가피한 경우(폼 프리필)는 레지스트리 스키마가 도착하면 사용자가 손대지 않은 값만 갱신해 스스로 정렬한다. 근거: 시뮬 탭이 항법 기본값 9개를 재기술해 그중 7개가 엔진과 어긋난 채(pos_std 1.0↔3.0, update_hz 50↔100 등) 돌던 사례 — 블록도는 엔진 값을 표시하는데 실행은 다른 값이라 무증상이었다 (v0.18)
- **[확정]** 파일 포맷 YAML + JSON 스키마 (§5.4와 동일 규격). 파라미터 스냅샷마다 **지문(fingerprint)** 발급 — 산출물 계보 추적·영향성 평가(§2.4)의 키
- 합격기준을 파라미터로 관리하면 판정 기준이 지문에 포함됨 — 산출물 계보에 요구도 버전이 자동 반영되고, 기준 변경 시 Δ리포트(§2.4)로 판정 변화 추적 가능

## 8. 사용자 워크플로우

**[확정]** 주 인터페이스는 웹 UI. 모든 단계는 CLI/Python API로도 수행 가능(엔진 우선 원칙).

1. 공력 DB(CSV/Excel) + 실속 경계 테이블 + 기체 파라미터 로드 → DB 뷰어로 이상 검사
2. 웹에서 트림 케이스 매트릭스 정의 → 배치 트림(진행률 모니터링) → 결과표·플롯
3. 트림점별 선형화 → 안정성·마진 맵 대시보드
4. 게인 스케줄 설계 — 웹 테이블 편집
5. 지도에서 웨이포인트 임무프로파일 편집 → 폐루프 시뮬 → 재생 + 엔벨로프 감시
6. 검증 리포트 생성·열람 (벤치마크/회귀 비교 포함)
