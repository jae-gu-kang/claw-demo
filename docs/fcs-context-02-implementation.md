## 1. 스코프

**[확정]** 범위는 **설계 · 해석 · 시뮬레이션**까지.
- 포함: 6DOF 플랜트, 트림, 선형화, 안정성 해석, 제어법칙 설계·실행, 비선형 시뮬레이션,
  검증·리포트
- **[확정]** **탑재 제어법칙 C 생성은 범위 안**이다 (v0.20에서 확대 — 종전 "FCC 탑재용 비행코드
  생성 제외, 별도 모듈로 추후 부착"을 대체). 전제: 생성 코드는 **FCC에 통합되어 그대로 실린다**.
  FCC팀이 신뢰성 시험을 거쳐 일부 수정할 수는 있으나 MATLAB 코드젠 산출물처럼 거의 그대로
  탑재된다
  - 여전히 범위 밖: **FCC 전체** — 주기 스케줄러, I/O(ARINC/1553/CAN), 입력 유효성·신선도,
    다중화·투표, BIT, 페일세이프 리버전, 모드 상태기계. 우리가 내는 것은 제어법칙 한 덩이다
  - **[확정]** 구조의 정본은 **IR 하나**이고, Python 실행과 C 생성은 그 **백엔드**다(07 §1,
    M16). 손으로 쓴 C를 따로 두지 않는다 — 제어법칙을 두 벌로 가지면 §5.5 중복 정의 금지를
    정면으로 어기고, 대조 테스트는 어긋남을 발견할 뿐 막지 못한다
  - **[확정] 한계** — 소스가 같아도 타깃 컴파일러·최적화 옵션·부동소수 폭 차이는 남는다. 측정
    사례: FMA 축약(`-ffp-contract=fast`)만 켜도 곱셈-덧셈이 합쳐져 비트 일치가 깨진다(최대
    2.8e-16, clang 14 -O2). 생성 헤더가 빌드 요구를 명시하되, **타깃에서의 확인(PIL 성격)은
    FCC팀 몫**이다. 과대 주장하지 않는다
  - 웹 코드 패널(06 §4)은 **두 가지를 나란히** 낸다: ① 설계 형상의 코드 표현(엔진 Python 재현
    스크립트 + C 파라미터 헤더, v0.17) — 탑재물이 아니라 검토·산출물용 ② **탑재 C**(v0.24) —
    위의 생성물 그 자체다. 웹은 C를 조립하지 않고 엔진 생성기(`POST /codegen/flight`)를 부르며,
    같은 형상이면 커밋된 산출물 `flight/gen/`과 바이트 단위로 같다. 두 탭이 내는 물건이 다르므로
    화면 안내 문구도 탭마다 다르다
- **[확정]** 개방망 우선 개발, 폐쇄망 적용 추후 검토 → **의존성 최소화** 설계 (프론트엔드 JS
  포함)

### 2.2 제어 요소 라이브러리 (Primitive Block Set)

**[확정]** 아래 원시 요소들이 C++ 코어의 구현 범위이자, 추후 코드젠 모듈의 생성 단위가 된다. 각
요소는 레지스트리+스키마 원칙(§2.3)을 따라 웹 UI에서 자동 편집 가능해야 한다.

| 분류 | 요소 |
|---|---|
| 기본 연산 | Gain, Sum, Product, Divide, Switch/Selector, Unit Delay, Memory |
| 적분·미분 | Integrator (안티와인드업 포함, 초기화 가능), Derivative |
| 선형 필터 | 1차 지연(Lag), Lead-Lag, Washout(HPF), Low-Pass, Notch, Discrete Filter, Zero-Pole, FIR/IIR, Moving Average |
| 제어기 | P / PI / PID (게인 스케줄 가능), State-Space, Transfer Function |
| 비선형 | Saturation, Rate Limiter, Dead Zone, **Backlash**, Hysteresis |
| 테이블 | 1D/2D/nD Lookup Table (보간·외삽 옵션) |
| 항공 전용 | Quaternion 연산, DCM, 좌표변환, 삼각함수 유틸 |
| 신호 관리 | Delay, Fader (범프리스 전환용), 상태 초기화 인터페이스 |

**[확정]** 그중 **레이트 피드백 경로에 놓을 수 있는 필터의 목록은 `blocks/filters.py`
`RATE_FILTERS` 한 표**다(none·washout·lowpass·notch, v0.30) — 마진
해석(`analysis.margins.filter_tf`)과 향후 법칙 그래프(`fcl.graphs`)가 같은 표를 읽는다. 어휘와
해석 표현의 어긋남은 import 시점 단정문이 막는다(`codegen/ir_exec.py`의
`assert set(_OP_FN) == set(OPS)`와 같은 가드). 목록 **안**에서 종류를 바꾸는 것은 값
편집이고(ParamDef `choices` 경유 — §5.5), 목록 **밖** 타입을 더하는 것은 C 에미터 1개 + 마진 TF
1개가 따르는 구조 변경이다.

- Simulink 사용 실적상 기본 블록(Integrator, Sum, Gain, Product, Saturation, Switch, Rate
  Limiter, Lookup Table, Unit Delay, Memory)이 전체의 절반 이상을 차지 → 이 집합의 구현
  품질·검증이 최우선
- **[확정]** 이 집합이 **탑재 C 생성의 단위**다 (M16 codegen). 제어법칙 구조의 정본은
  IR이고(07 §1) 블록 구현은 백엔드다 — 블록의 Python `step()`과 C 에미터는 같은 명세의 두
  구현이므로 **블록별 등가성 대조로 못박는다**. 이건 §5.5 중복 정의 금지의 예외가 아니라 성격이
  다른 것이다: 블록 집합은 **고정·유한(25종)** 이라 대조로 관리되지만, 제어법칙 구조는 계속
  바뀌므로 반드시 단일 정본이어야 한다 (MathWorks도 시뮬 엔진과 TLC 템플릿으로 블록을 이중
  구현하고 SIL/PIL로 대조한다)

**IR·코드젠 결정은 [`fcs-context-07-ir-and-backends.md`](fcs-context-07-ir-and-backends.md)가
정본이다** — 구조의 정본이 IR 하나라는 것, C 생성 가능 제약, enable 영역, 생성물의 역할축·기능축
분할, 이산 계수 굽기와 형상 지문, 입력 경계, 비트 일치 검증이 거기 있다. 이 절은 **블록 집합
자체**만 다룬다.

### 2.3 계층 구조

**[확정]** 최종 형상은 C++ 코어 + Python 해석층 하이브리드. 단, 개발 전략은 **Python 레퍼런스
우선** (모듈 문서 03 §7.1 채택):
- Phase 1~4의 코어(제어 요소·보간·환경·플랜트·법칙 실행부)는 순수 Python(NumPy/SciPy) **레퍼런스
  구현**으로 완성. 코어 경계 API를 고정해 두고, 성능이 문제 되는 시점(몬테카를로·배치 규모
  확대)에 pybind11 기반 C++ 구현으로 **드롭인 교체**
- Python 레퍼런스판은 폐기하지 않고 C++판의 **회귀 기준(oracle)** 으로 상시 유지 — 이중 구현이
  아니라 검증 자산
- **[TBD]** **제어법칙 C 백엔드로의 전환 시점** — 제어법칙 구조가 굳은 뒤로 미룬다. 01 §7 미결
  중 엘레본 믹싱 비율·경로추종 알고리즘·모드 전환 조건·저고도 플레어는 **구조를 바꾸는**
  항목이고, 공력 DB·작동기 특성·실속 경계가 아직 [기본값] 가정값이다. 굳지 않은 설계를 C로 먼저
  쓰면 C를 계속 고치게 된다 — 개발 속도가 아니라 재작업 비용이다. 구조 정본이 IR이므로(07 §2) 이
  전환은 다시 쓰기가 아니라 **백엔드 추가**이고, 그래서 미뤄도 부채가 되지 않는다

| 계층 | 언어/기술 | 담당 |
|---|---|---|
| 코어 라이브러리 | C++ (선행: Python 레퍼런스) | 공력 DB 보간, 6DOF 운동방정식, 작동기, 추진, 대기모델, 적분기, 제어법칙 실행 |
| 바인딩 | pybind11 | C++ 코어의 Python 노출 |
| 해석층 | Python | 트림(scipy.optimize — SLSQP/trust-constr), 선형해석(python-control), 배치실행, 플롯·리포트 |
| 백엔드 | Python + FastAPI **[확정]** | REST API, 작업 실행(배치 트림/시뮬), 웹소켓 진행률, 결과 저장 |
| 프론트엔드 | 웹 — 바닐라 ES 모듈, no-build **[확정]** | §4 운영 전제 · 화면은 06 |

- 근거: 시뮬 속도 + 추후 실시간/HIL 모듈에서 검증된 동일 C++ 코드 재사용 + 해석은 Python 생태계
- **[확정]** 실시간성 고려: 코어는 동적할당 최소화 등 실시간 친화 코딩 스타일
- **[확정 설계원칙]** **엔진 우선**: 엔진을 CLI/Python API로 먼저 완성, 웹 UI는 동일 API를
  소비하는 별도 층 (UI가 엔진 개발을 막지 않도록)
- **[확정 설계원칙]** **샘플레이트 최상위 파라미터화**: 이산화 계수 하드코딩 금지, 주기(100→50
  Hz 등)로부터 자동 계산. 주기 변경 시 이산 제어기 포함 위상여유 재계산 + 응답 비교 자동화 기능
  제공
- **[확정 설계원칙]** **레지스트리 + 파라미터 스키마**: 교체 가능 컴포넌트(경로추종 알고리즘,
  적분기, 필터 등)는 자신의 파라미터 정의(JSON 스키마)를 노출. UI는 스키마로부터 폼 자동 생성 —
  새 컴포넌트 추가 시 UI 코드 수정 불필요

### 2.4 설계값 연계·정량 영향성 평가

**[확정 — 신규 요구]** 모듈 간 설계값은 유기적으로 연계되며, 어느 단계의 수치 변경이든 전체
출력에 미치는 영향을 정량 평가할 수 있어야 한다.

- **계보(lineage) 추적**: 모든 설계 산출물(트림표, 선형모델, 마진 맵, 시뮬 결과)은 자신이 계산된
  파라미터 스냅샷의 **지문(fingerprint)** 을 기록한다 (§5.5 파라미터 계층이 지문 발급)
- **[확정]** 지문 대상 확장: ParamSet뿐 아니라 **입력 데이터 파일(공력 DB, 실속 경계 테이블)의
  해시·버전**도 산출물 계보에 기록 — "어떤 DB 버전 + 어떤 파라미터 버전으로 계산됐는지" 재현
  가능해야 Simulink 회귀 대조(§7)가 성립
- **설계 파이프라인 DAG**: params → 트림 → 선형화 → 마진 → 시뮬의 산출물 의존 그래프를 관리.
  파라미터 변경 시 영향받는 산출물만 자동 무효화·증분 재계산
- **정량 Δ리포트**: 변경 전/후 두 파라미터 스냅샷에 대해 파이프라인을 재실행하고 차이를 정량
  비교 — 트림점 이동, 고유치·감쇠비·이득/위상여유 변화,
  응답지표(오버슈트·정착시간)·경로오차·실속마진 변화
- **파라미터 스윕/민감도**: 지정 파라미터를 격자로 흔들어 출력 민감도 산출 (배치 실행 재사용)
- 기존 100 vs 50 Hz 마진 비교(§2.3 샘플레이트 원칙)는 이 기능의 특수 사례로 흡수
- **[확정] 영향 매핑은 손으로 적지 않는다** — "이 게인이 저 노드를 건드린다"를 표로 두면
  구조 정본(M16 IR)이 바뀔 때 조용히 낡는다(§5.5 중복 정의 금지가 막는 것이 이것이다).
  파라미터를 흔들어 법칙을 **재조립하고 노드 서명을 diff** 해서 매핑을 유도한다. 부수
  효과로 **구조를 바꾸는 파라미터**도 잡힌다 — `k_thr_turn` 0→ε은 노드 4개를 새로
  만들고(안 쓰이는 경로는 생기지 않으므로) 그건 민감도가 아니라 위상 변경이다
- **[확정] 세 상태를 구분해 보인다** — 같은 "도달"이라도 성격이 다르고, 뭉뚱그리면
  사용자가 "왜 편집해도 안 먹지"를 혼자 알아내야 한다:
  ① **덮임** — 게인 스케줄이 붙은 SCAS 상수는 그래프에 있지만 실행기가 매 스텝 게인
  포트로 덮어쓴다(`inst.step(u, **gains)`) → 구조 diff에는 잡히고 런타임 효과는 0
  ② **미방출** — 스케줄된 `k_rate`는 상수 대신 조회 노드를 쓰므로 그래프에 **없다**
  ③ **법칙 밖** — 항법·작동기·유도는 IR 바깥이라 개루프가 못 본다. "영향 없음"이 아니다
- **[확정] 도달성은 크기가 아니다** — 포화된 가지나 0 게인을 지나는 경로도 도달로 잡힌다.
  「얼마나」는 개루프 Δ(2단)·폐루프 스윕(3단)의 몫이고, 화면이 그 구분을 말해야 한다
- 담당: 모듈 문서(03) M15 `pipeline`

## 3. 모듈 구성

**[확정]** 현행 Simulink 서브시스템 구조를 따라 아래 6개 모듈로 구성한다.

| 모듈 | 담당 | 주요 요소 |
|---|---|---|
| 1. Flight Control | SCAS, 오토파일럿, 게인 스케줄링, 엘레본 믹싱(제어 할당) | PID, State-Space, 필터, 게인 테이블 |
| 2. Guidance | 경로 생성·추종, 비행모드 실행기 | 경로추종 알고리즘, 웨이포인트 로직, 모드 테이블 |
| 3. Navigation | 항법 상태 추정 출력 제공 | **등가 오차 모델** (§3.1) — EKF 미구현 |
| 4. Actuator | 작동기 동특성 | Transfer Function/State-Space, Rate Limiter, Dead Zone, Backlash |
| 5. Sensor | IMU/GPS 모델 | 노이즈, 지연 (초기에는 이상 센서) |
| 6. Aircraft Dynamics | 6DOF, 공력, 추진, 대기·중력·지구모델 | Lookup Table, Quaternion, 좌표변환, 적분기 |

### 3.1 항법(Navigation) 모듈 — 등가 오차 모델

**[확정]** 툴은 EKF를 구현하지 않는다. Navigation 모듈은 실제 항법(EKF) 출력의 **통계적 특성을
재현하는 등가 오차 모델**로 구현한다.

```
항법 출력 = 참값(6DOF) + 오차(백색잡음 + 상관잡음/바이어스) + 지연
```

**근거**
- 툴이 EKF를 구현해도 실제 비행할 항법팀의 EKF와는 다른 근사물 → 현실성 착시만 유발
- 등가 오차 모델은 실제 EKF의 **성능 수치**(공분산, 지연)를 그대로 반영 가능 → 재구현보다 실제에
  근접
- 제어루프가 느끼는 것은 제어대역 대비 빠른 잡음과 느린 바이어스뿐이며, 추정기 내부 구조는
  제어기 설계에 영향 없음
- 항법은 별도 전문 영역 — 중복 개발 회피

**인터페이스 개방**: Navigation 모듈은 교체 가능 컴포넌트(레지스트리, §2.3)로 등록하여, 추후
항법팀의 실제 EKF 모델이나 비행소프트웨어 코드를 그대로 꽂을 수 있게 한다.

**오차 모델 파라미터** (상태별로 정의)
| 항목 | 내용 |
|---|---|
| 백색잡음 | 표준편차 (위치/속도/자세/각속도별) — **위치·속도는 수평(N·E)/수직(D) 분리** (01 §2.5 [기본값]) |
| 바이어스 | 초기 바이어스 + 상관시간(1차 마르코프) — 위치축, **수평/수직 분리** |
| 지연 | 항법 출력 지연 (transport delay) |
| 갱신주기 | 항법해 출력 주기 |

**[기본값]** 초기값은 GPS/INS 통합항법의 일반적 수준으로 시작한다. 항법팀의 실측·공분산 해석
자료 확보 시 대체.
- 위치: 수 m 급 (수평/수직 구분)
- 속도: 0.1~0.5 m/s 급
- 자세(롤·피치): 0.1° 내외 / 방위: 롤·피치 대비 큼
- 지연: 수십 ms 급
- 갱신주기: 제어주기(100 Hz)와 동등하거나 낮음 → 멀티레이트 처리 필요
- **[TBD]** 구체 수치는 항법팀 자료 확보 시 확정. 위 값들은 자리표시자(placeholder)

### 5.6 비행체 프로파일 (기체 > 형상 변형)

- **[확정]** 툴은 특정 기체를 전제하지 않는다. 기체 데이터는 전부 **프로파일 문서** 하나에
  있고 코드·웹은 기체 값을 갖지 않는다. 03 §7.2 「프로파일 교체」의 구현이며 모듈은 M18
  `profile`이다(03 §3). 계층은 **기체 > 형상 변형**이고 사업 층은 두지 않는다
- **[확정]** 문서는 JSON이고 정본은 검증기 `engine/claw/profile/schema.py`다. 섹션은
  geometry·aero·stall·mass·propulsion·actuator·surfaces·structural·operating·ground·trim·law·
  variants이며, 필드와 범위는 검증기가 정본이라 여기 다시 적지 않는다. 검증 규칙:
  - 모르는 키는 거부한다 — 오타가 조용히 무시되면 "입력했는데 반영 안 된 값"이 된다
  - 레지스트리 컴포넌트(추진·작동기·SCAS 축·자동조종)는 파라미터를 **전부 명시**한다 —
    02 §5.5의 "엔진 기본값 재기술 금지"와 반대 방향의 같은 규칙이다: 기체 문서에서는
    레지스트리 기본값이 곧 어느 한 기체의 값이라, 보충하면 기체를 조용히 전제하게 된다
  - **null은 "없음"이다** — 허용된 자리(q̄_max·운용 고도·DB 범위·지상장치·설계 게인·스케줄·
    할당)에서만 쓰고, 예제 값으로 채우지 않는다. 필수 수치의 null은 오류다
  - 수치는 float로 정규화한다 — 저장본의 6과 6.0이 지문·응답 바이트를 가르지 않게
  - SCAS 출력 한계와 작동기 위치 한계는 문서 항목이 아니다 — surfaces에서 온다(중복 정의 금지)
- **[확정] 공력 계수는 항의 합이다** — 항 = k × 입력의 곱(상수항·타면 증분·동미계수가 모두 이
  꼴). 형식은 풍축 `lift_drag`(CD 항에 CL 입력 허용, 동체축 변환은 plant
  `wind_to_body_coeffs`)와 동체축 `body` 둘이다. 섭동 태그(`cmalpha`·`cmq`)가 붙은 항만 강건성
  검증(04)이 흔들 수 있고, 태그가 없는 축을 흔들면 조립이 거부한다 — 흔드는 시늉은 조용한 거짓
  합격이다
  - **[확정] 연산 순서가 계약이다**: 합은 0.0이 아니라 첫 항에서 시작해 왼쪽부터 접고, 곱은
    k부터 입력 순서대로, 섭동은 k를 먼저 k·(1+d)로 만들며, 빠진 타면 입력은 0.0으로 읽되 항을
    건너뛰지 않는다. 0.0에서 시작하면 −0.0이 +0.0으로 바뀌어 예제 산출이 비트 단위로 달라진다
  - **[백로그]** 표 항(N-D Table)과 고도 입력 — 3-D 표 조회가 해석식보다 한 자릿수 이상 느려
    전용 보간기와 속도 예산 테스트가 전제다
- **[확정] 형상 변형은 JSON Pointer 치환 맵이다** — `{"/mass/m_empty": 900.0}`. RFC 7386 merge
  patch를 쓰지 않는 것은 거기서 null이 "키 삭제"라 이 문서의 "없음"과 한 기호에 겹치기 때문이다.
  어느 항목이든 덮어쓸 수 있고(식별 항목·variants 제외), 없는 경로는 오타로 거부하며, 적용한 뒤
  문서 전체를 다시 검증한다
- **[확정] 지문은 둘이다**(규격은 `canonical_hash` 하나) — `profile_fp`는 적용된 문서에서
  이름표·자유 텍스트 출처와 계산에 쓰이지 않는 화면 기본값(미션 템플릿)을 뺀 것으로 **계보
  도장**이고(02 §2.4의 입력 데이터 해시의 기체 쪽 구현 — 결과 meta·응답의 `profile` 블록이
  싣는다), `plant_fp`는 트림이 보는 섹션만이라 파생 표(δe_trim 등)가 낡았는지를 판정한다. 제외
  목록은 `profile/fingerprint.py FP_EXCLUDED`가 정본이고 테스트가 고정한다 — 목록이 넓어지면
  "같은 기체"의 정의가 조용히 넓어진다
- **[확정] 미션 템플릿(`mission_template`)은 화면 기본값이고 선택 절이다** — 해석 격자(트림·마진
  맵·영향성·게인 카드)·엔벨로프 선도 조건과 스캔 격자·시뮬 기본 미션의 기체 성능
  값(속도·상승각·고도·연료·도달 반경)·착륙 미끄럼 거리. 기체 성능에 맞춰 잰 값이라 기체마다
  다르지만 계산 입력이 아니다 — 결과는 실제로 보낸 요청을 싣는다. 그래서 지문 밖이다. 스키마
  v1에 나중에 더한 절이라 문서에 없으면 없음(null)으로 채우고 버전을 올리지 않았다: 버전을
  올리면 버전 값이 지문에 들어가 옛 결과·설계 세션의 계보(스냅숏 지문)가 통째로 끊긴다. 계산에
  쓰이는 절이 생기면 그때 버전을 올리고 업그레이더를 둔다. 장소 값(경로·활주로)은 들이지 않는다
  — 기체가 아니라 시험장이다. 격자는 200케이스까지다(서버 스캔·영향성 상한과 같다) — 간격 오타
  하나로 그 기체를 고른 모든 화면이 격자를 만들다 멈추지 않게. 없음이면 웹이 예제 기체에 맞춘
  폴백을 쓰고 화면이 그렇다고 말한다(06 §8)
- **[확정] 구 데모 델타윙은 읽기 전용 예제다** — `engine/claw/profile/examples/delta_demo.json`
  (패키지 데이터). 실기체 값이 아니다. 이관 전후 산출이 같다는 증거는 이관 전 HEAD에서 굳힌
  **골든**이다(`engine/claw/tests/golden` · `server/tests/claw_server/golden`): 부동소수를
  `float.hex()`로 굳혀 비트 단위로 비교한다 — 허용오차 비교는 연산 순서가 바뀐 1-ulp 차이를
  삼키는데, 그 차이가 곧 "옮기다 식을 바꿨다"는 증거라 삼키면 안 된다. dict 키 순서도 비교한다
- **[한계]** 타면 배치와 법칙 템플릿은 하나(`elevon4_rudder1`·`delta_elevon_v1`)만 받는다 — 다른
  배치는 검증이 거부한다. CG 입력은 공력 모멘트 기준점 이전(02 §5.1 [TBD])이 없어 동역학에
  반영되지 않는다
- **[확정] 소비자는 기체를 프로파일에서 받는다** — 제품 코드(엔진·서버·생성기)는
  `plant/demo.py`·`fcl/demo.py`를 부르지 않는다. 두 모듈은 예제 문서를 감싸는 호환 층이라
  테스트만 쓰고, import 자체를 가드 테스트(`engine/claw/tests/test_profile_guard.py`)가 막는다 —
  제품 코드가 부르면 예제 기체로 계산하고 선택한 기체의 이름을 붙이게 된다
  - 법칙 조립 정본은 `fcl/assemble.py assemble_law(profile, …)`다(02 v0.24 「조립 정본은
    하나」의 자리 이동). 설계 게인이 없는 프로파일(`law.design` null)은 주입 없이 조립하면
    경로가 붙은 오류다 — 없는 게인을 지어내지 않는다
  - 해석 형상 `Shape`가 `profile`을 들고 다닌다 — `make_law`·`evaluate`·`verify`·`run_sweep`이
    거기서 실속표·DB 범위·설계값을 읽는다. **형상 지문 밖이다**: 형상 지문은 사용자가 정한
    덮어쓰기의 계보이고 기체의 계보는 `profile_fp`가 맡는다 — 그 지문은 결과 meta·응답의
    `profile` 블록에 실린다. 부분 덮어쓰기(자동조종·SCAS·믹서)는 레지스트리 기본값이 아니라 **그
    기체의 설계값** 위에 얹힌다
  - 트림 탐색 범위(α·δe)와 트림 α 여유는 모듈 상수가 아니라 `Aircraft.trim_bounds`다 — 조립기가
    채우고, 없으면 트림이 거부한다. δe 범위는 엘레본 한계 그 자체라 믹서와 같은 값을 읽는다
  - `evaluate`·`verify`는 기체의 `plant_fingerprint`가 형상의 프로파일과 다르면 거부한다(A
    기체를 B 기체의 법칙·표로 평가하는 조합). 강건성 코너는 프로파일이 흔들 수 있는 축과의
    교집합만 만들고, 빠진 축은 판정 불가로 경고한다
  - 서버 라우트는 기체를 `claw_server/refs.py resolve_profile(request, ref)` 한 곳에서만
    받는다(아래 저장·선택)
- **[확정] 저장·선택·계보 (서버)** — 기체 문서는 웹에서만 만들고 고치며, 서버가 검증해
  **리비전으로** 쌓는다
  - 저장소는 `claw_server/profiles.py ProfileStore`다(`$CLAW_PROFILE_DATA`, 기본은 결과 루트
    아래 `profiles/`). 결과 저장소를 재사용하지 않는다 — 그쪽은 보존 상한에서 오래된 것을
    지우는데 기체 문서는 결과·설계 재개가 기대는 원본이다. 갱신은 `base_revision`이 최신과 같을
    때만 받고 아니면 409다 — 두 화면이 같은 기체를 고치면 나중 저장이 앞의 것을 조용히 덮지
    않는다. 예제 기체는 엔진 패키지 데이터라 읽기 전용(리비전 0)이고, 고치려면 복제한다.
    내보내기는 조회, 가져오기는 생성과 같은 경로다. 기체 id는 `_`로 시작할 수 없다(저장소 내부
    폴더 자리). 삭제는 목록·조회에서만 빼고 리비전 파일을 남겨, 같은 id로 다시 만들면 리비전
    번호를 **이어 센다** — 옛 결과의 (id, 리비전)이 새 문서를 가리키면 안 된다. (id, 리비전)은
    한 문서를 영원히 가리킨다 — 다시 만든 기체에서 옛 번호를 고르면 지운 기체의 문서다. 저장본은
    읽을 때마다 다시 검증하고, 손상됐거나 스키마가 바뀌어 못 넘으면 409다. head를 못 읽는 기체는
    조회·갱신·생성이 409이고 삭제만 받는다 — 치운 뒤 다시 만드는 복구 경로다. 저장 없는 검증은
    저장과 같은 규칙이다(검증이 통과시킨 문서를 저장이 거부하지 않는다). 형상 변형은
    64개까지다(읽을 때마다 변형마다 재검증한다)
  - 선택은 요청 본문의 `profile: {id, variant?, revision?}`(GET은
    `profile_id`·`profile_variant`·`profile_revision`)다. 고르지 않으면 예제 기체이고
    `source: "default-example"`로 그 사실을 echo한다. 없는 기체·변형은 404다 — 조용히 예제로
    계산하지 않는다
  - 계산 결과의 meta·본문과 동기 응답이 `profile`
    블록(id·name·variant·revision·fingerprint·plant_fingerprint·is_example·source)을 싣는다.
    해석한 **적용 문서**는 지문을 이름으로 스냅숏에 남고 기체를 지워도 지우지 않는다 — 옛 결과가
    무엇으로 계산됐는지를 말할 수 있어야 한다. 설계 세션 재개는 그 스냅숏으로 같은 기체를
    되살린다(기체 기록이 없는 옛 세션은 예제로 이어가고 `legacy-unrecorded`로 표시). 스냅숏의
    이름표는 믿지 않는다 — 지문이 이름표를 빼므로 같은 지문을 다른 이름의 기체(예제를 복제만 한
    기체)가 먼저 남겼을 수 있다. 재개는 스냅숏으로 조립하되 이름표는 저장된 echo에서 가져온다.
    스냅숏도 재개할 때 다시 검증해, 못 넘으면 409다. 저장 결과를 읽어 계산하는 라우트는 결과의
    기체 지문과 요청 기체를 대조한다 — 진단은 경고, 처방은 409다(다른 기체의 스윕으로 풀고 이
    기체로 확인하면 처방과 확인이 서로 다른 기체를 말한다)
  - 서버가 복제하던 기체 값 — V-n α 보호 마진·음의 실속 자리표시 비율·발사 레일 높이 기본값 — 은
    요청이 비우면 프로파일에서 읽는다. 구조 한계 출처 echo는 덮어쓰면 `user-input`, 사용자
    기체면 `profile`, 예제면 종전 `demo-placeholder`다
- **[확정] 웹 선택** — 헤더에서 기체·형상 변형을 고르고 브라우저에 둔다. 어느 계산 요청에
  싣는가는 `web/js/lib/profile.js` 한 곳이고, 전환은 페이지를 다시 읽는다 — 규칙과 근거는 06 §8.
  절별 편집 폼의 칸 서술(이름·단위·형식·선택지)은 검증기 옆 `profile/form.py`가
  `GET /profiles/_form`으로 준다
- **[백로그]** 서브시스템 페이지 설계값 서술의 기체 문서화(06 §7) · 표 공력 DB와 DB 뷰어(02
  §5.2) · 초기 게인 빠른 탐색과 δe_trim 도출 · 트림 reserve와 가용 동적 여유 · 항법 장비 · LLM
  기체 문맥 · 3D 표시 모델 · 대조 미션(`verify/trace.py`의 시작 트림·경로)의 기체별 미션 템플릿

#### 5.6.1 예제 기체 — 수치의 근거

예제 기체의 값은 `engine/claw/profile/examples/delta_demo.json`에 있고, 그 값이 **왜 그
값인지**는 여기 있다(문서 규약 4). 종전에는 `plant/demo.py`·`fcl/demo.py` 주석이었다 — 값이
문서로 옮기면서 근거도 함께 옮겼다. 전부 예제용 라운드 값이고 실기체 값이 아니다. 항목 머리는
문서 경로다.

- `/ground/skid` — 강성은 **정지 침투량**으로 정했다: 총중량 10.8 kN을 5 cm에서 받으려면 k_total
  ≈ 216 kN/m, 4점이라 점당 54 kN/m. 감쇠는 ζ≈0.7로 ω_n = √(k_total/m) ≈ 14 rad/s → c_total ≈
  21.6 kN·s/m, 점당 5.4 kN·s/m. 접촉 고유주파수 2.2 Hz라 dt_plant 0.005~0.01의 RK4가 충분히
  분해한다. μ 0.35는 바퀴가 아니라 미끄럼 값이다
  - 좌·우 스키드를 앞·뒤 2점씩 4점으로 둔다 — 좌우 2점만이면 피치 자유도가 없어 접지 후 기수
    내려앉음이 나오지 않는다
  - 접촉점 중심을 CG에 맞췄다(x 대칭) — 어긋나면 수평 자세가 평형이 아니다(Δx 0.10 m면 정지 상태
    M_y 1.08 kN·m 기수 올림). 활주 이륙이면 CG를 주기어 앞에 두어 회전을 얻지만 발사대 이륙이라
    수평 정지가 더 쓸모 있다
- `/ground/rail/origin_height` 2.9 m — 0이면 스키드 접촉점(CG 아래 0.55 m)이 지면 0.55 m 아래에
  박힌 채 출발해 레일 구간 내내 wow·기어 반력이 거짓으로 선다. 발사관 시각화 모델의 캐니스터
  축(관 뒤끝 기준 2.83 m, `models/launcher/README.md` 2026-09-02 2차 개정 실측)에 맞춰 기체가 관
  속에서 사출되는 그림이 되고, 접촉점(지면 위 2.35 m)은 지면에 닿지 않는다
- `/ground/rail` 10 m·15°·81.5 m/s — 이탈 속도는 트림 정합 실속속도 70.9 m/s의 1.15배다. α_stall
  0.40에서 CL 1.40이 나오지만 거기까지 가려면 상향 엘레본이 양력을 깎으므로(Cm = 0.02 − 0.8α −
  1.0δe = 0 동시 만족) 실제 최대 트림 CL은 1.169다. 레일 10 m에서 이 속도는 33.9 g를 요구하고,
  판정 기준 `n_x_launch`가 [TBD]라 「미판정」으로 표시된다
- `/propulsion` 프로펠러 500 kW·η 0.8·정지추력 6 kN — 상수 추력에서 프로펠러 곡선으로 옮긴
  목적은 엔벨로프 상단이 **추력으로** 잘리게 하는 것이다(정지추력 유도는 `plant/prop.py
  PropEngine`). 축동력 500 kW는 실측으로 정했다: 300 kW에서는 3000 m 트림이 안 되고 전 구간
  스로틀 78~95%라 상승·선회 여력이 없었다(1200 kg에 날개 3 m², 실속 71 m/s). 500 kW에서 최대
  스로틀 0.74로 여유가 서고 프로펠러 성격(순항 M0.3~0.4, 상단이 추력으로 막힘 — 해면 M0.60@연료
  200, M0.58@만재)은 남는다. 종전 상수 8 kN은 M0.8에서도 여유가 있었지만 해면 환산 소요 축동력
  1,012 kW라 프로펠러가 낼 수 없는 값이었다
- `/aero/db_ranges` — 마하 하한 0: 예제 계수는 마하를 쓰지 않으므로(M0.15와 M0.85가 같다) 종전
  하한 0.1은 데이터의 성질이 아니라 대역 서술이었고, 그 값 때문에 해면 34 m/s 아래(발사
  레일·착륙 미끄럼 구간 전체)에 마하 플래그가 서서 엔벨로프 요약(any_flag)이 상시 참이 됐다.
  상한 0.9는 천음속에서 선형식이 무의미해진다는 실제 주장이라 남긴다. CFD DB가 들어오면 둘 다
  DB의 실제 축 범위로 바뀐다

게인·마진 맵의 앞뒤도 탭 줄과 반대였다. 코드 주석의 `02 §8 N단계` 인용도 함께 옮겼다.
v1.04에서 맨 앞에 **0단계(기체)**를 세웠다 — 번호를 한 칸씩 밀면 코드·문서의 `02 §8 N단계`
인용이 전부 조용히 옆 단계를 가리키므로, 뒤를 밀지 않고 앞에 0을 붙였다.

0. 기체 프로파일 선택·생성·편집 — 헤더에서 고른 기체(와 형상 변형)가 이후 모든 단계의 입력이다.
   공력 DB·실속 경계·질량·추진·작동기·구조 한계·설계 게인이 한 문서(02 §5.6)이고, 예제는 읽기
   전용이라 복제해서 고친다. 공력 DB의 조건별 곡선 교차확인(DB 뷰어)은 아직 없다 [기체]
1. 제어법칙 구조를 블록 다이어그램 허브에서 훑는다 — 서브시스템 내부 페이지·설계 노트·파라미터
   폼. 공력 DB·기체 파라미터 로드는 0단계 기체 문서의 몫이다 [블록도]
2. 설계 엔벨로프 확정 — 구조(V-n)·공력(α–Mach)·추진·운용 선도를 M-h 평면에 합성,
   트림 스캔으로 제어 가능 영역 판정 (뒤 단계의 격자 범위·α 여유 기준) [엔벨로프]
3. 트림 케이스 매트릭스 정의 → 배치 트림(진행률 모니터링) → 결과표·플롯 [트림]
4. 게인 스케줄 설계 — 웹에서 **스케줄 자리 선택**(형상) 후 테이블 값 편집 [게인]
5. 트림점별 선형화 → 안정성·마진 맵 대시보드 (설계 게인의 선형 검증) [마진 맵]
6. 자동 설계 — 트림 격자 자동화 → 게인 자동 튜닝 → 다항 스케줄 적합 → 보간 실효
   게인 마진 검증 → 원인별 처방 이터레이션 (승인 게이트) [자동 설계]
7. 지도에서 웨이포인트 임무프로파일 편집 → 폐루프 시뮬 → 재생 + 엔벨로프 감시
   [시뮬레이션]
8. 그 궤적을 실지형 3D에서 확인 — 지형·웨이포인트·카메라 4종 [가상환경]
9. 케이스 격자 전체로 6DOF 판정 — 카드 7·판정 10 → 국소성·소견 → 처방 → 3단계 검증.
   7·8의 런을 넘겨받아 자기 미션의 결함을 귀속하는 수동 진단도 여기다 [영향성]
10. 통과한 형상의 탑재 C 생성·열람 [Autocode]
11. 생성 C를 DAL A 기준으로 검증 — 정적 규율·엄격 컴파일·비트 대조·MC/DC →
    증적 보고서 (벤치마크/회귀 비교 포함) [검증]
12. 산출물 목록·계보 지문 열람 — 단계가 아니라 아무 때나 여는 자리다 [결과]

**7·8이 9 앞인 것은 관습이 아니라 구조다** (v0.66, 사용자 지적 "시뮬을 돌리고
난 후에만 볼 수 있는 평가들이 있잖아 — 이거 자체가 탐색이 아니었다는 근거 아니야?").
9의 판정 카드는 6DOF 런 없이는 **값 자체가 없다**: `evaluate(depth="linear")`는
시뮬 0이라 tracking·envelope·actuator·recovery·coupling 다섯 단계가 통째로 사유를
든 na가 되고(`pipeline/evaluate.py` — "비선형 런 없음(depth=linear) — 단계 2에서
잰다"), 잔여 권한은 "런에서 잰다", 원인 귀속은 "런의 내부 기여항에서 나온다",
총점 J는 "비선형 항(RMS·Mp·δ) 미계측"으로 빠진다. 즉 **시뮬레이션은 판정의
입력이지 곁가지 탐색이 아니다** — v0.60이 "시뮬은 탐색이라 단계가 아니다"라고
적을 때 틀린 것은 사실이 아니라 추론이었다: "시뮬 탭 런은 판정 격자 런과 다르다"
(참, 지금도 참)에서 "그러므로 시뮬레이션은 단계가 아니다"(거짓)로 건너뛰었다.
다만 9가 쓰는 런은 9가 **자기 안에서** 도는 표준 진단 기동이다(케이스마다 표준
기동 런 + 동시명령 런 — `routes/influence.py` submit_evaluate). 표준화된 기동이라야
케이스끼리 비교가 되므로 이 분리는 유지된다: 7의 런은 판정에 들어가지 않고 9의
**수동 진단**(자기 미션 귀속)으로 간다.
