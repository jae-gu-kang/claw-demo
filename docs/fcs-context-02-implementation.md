## 1. 스코프

**[확정]** 범위는 **설계 · 해석 · 시뮬레이션**까지.
- 포함: 6DOF 플랜트, 트림, 선형화, 안정성 해석, 제어법칙 설계·실행, 비선형 시뮬레이션, 검증·리포트
- **[확정]** **탑재 제어법칙 C 생성은 범위 안**이다 (v0.20에서 확대 — 종전 "FCC 탑재용 비행코드 생성 제외, 별도 모듈로 추후 부착"을 대체). 전제: 생성 코드는 **FCC에 통합되어 그대로 실린다**. FCC팀이 신뢰성 시험을 거쳐 일부 수정할 수는 있으나 MATLAB 코드젠 산출물처럼 거의 그대로 탑재된다
  - 여전히 범위 밖: **FCC 전체** — 주기 스케줄러, I/O(ARINC/1553/CAN), 입력 유효성·신선도, 다중화·투표, BIT, 페일세이프 리버전, 모드 상태기계. 우리가 내는 것은 제어법칙 한 덩이다
  - **[확정]** 구조의 정본은 **IR 하나**이고, Python 실행과 C 생성은 그 **백엔드**다(§2.2, M16). 손으로 쓴 C를 따로 두지 않는다 — 제어법칙을 두 벌로 가지면 §5.5 중복 정의 금지를 정면으로 어기고, 대조 테스트는 어긋남을 발견할 뿐 막지 못한다
  - **[확정] 한계** — 소스가 같아도 타깃 컴파일러·최적화 옵션·부동소수 폭 차이는 남는다. 측정 사례: FMA 축약(`-ffp-contract=fast`)만 켜도 곱셈-덧셈이 합쳐져 비트 일치가 깨진다(최대 2.8e-16, clang 14 -O2). 생성 헤더가 빌드 요구를 명시하되, **타깃에서의 확인(PIL 성격)은 FCC팀 몫**이다. 과대 주장하지 않는다
  - 웹 코드 패널(§4)은 **두 가지를 나란히** 낸다: ① 설계 형상의 코드 표현(엔진 Python 재현 스크립트 + C 파라미터 헤더, v0.17) — 탑재물이 아니라 검토·산출물용 ② **탑재 C**(v0.24) — 위의 생성물 그 자체다. 웹은 C를 조립하지 않고 엔진 생성기(`POST /codegen/flight`)를 부르며, 같은 형상이면 커밋된 산출물 `flight/gen/`과 바이트 단위로 같다. 두 탭이 내는 물건이 다르므로 화면 안내 문구도 탭마다 다르다
- **[확정]** 개방망 우선 개발, 폐쇄망 적용 추후 검토 → **의존성 최소화** 설계 (프론트엔드 JS 포함)

### 2.2 제어 요소 라이브러리 (Primitive Block Set)

**[확정]** 아래 원시 요소들이 C++ 코어의 구현 범위이자, 추후 코드젠 모듈의 생성 단위가 된다. 각 요소는 레지스트리+스키마 원칙(§2.3)을 따라 웹 UI에서 자동 편집 가능해야 한다.

| 분류 | 요소 |
|---|---|
| 기본 연산 | Gain, Sum, Product, Divide, Switch/Selector, Unit Delay, Memory |
| 적분·미분 | Integrator (안티와인드업 포함, 초기화 가능), Derivative |
| 선형 필터 | 1차 지연(Lag), Lead-Lag, Washout(HPF), Low-Pass, Notch, Discrete Filter, Zero-Pole, FIR/IIR, Moving Average |

**[확정]** 그중 **레이트 피드백 경로에 놓을 수 있는 필터의 목록은 `blocks/filters.py` `RATE_FILTERS` 한 표**다(none·washout·lowpass·notch, v0.30) — 마진 해석(`analysis.margins.filter_tf`)과 향후 법칙 그래프(`fcl.graphs`)가 같은 표를 읽는다. 어휘와 해석 표현의 어긋남은 import 시점 단정문이 막는다(`codegen/ir_exec.py`의 `assert set(_OP_FN) == set(OPS)`와 같은 가드). 목록 **안**에서 종류를 바꾸는 것은 값 편집이고(ParamDef `choices` 경유 — §5.5), 목록 **밖** 타입을 더하는 것은 C 에미터 1개 + 마진 TF 1개가 따르는 구조 변경이다.
| 제어기 | P / PI / PID (게인 스케줄 가능), State-Space, Transfer Function |
| 비선형 | Saturation, Rate Limiter, Dead Zone, **Backlash**, Hysteresis |
| 테이블 | 1D/2D/nD Lookup Table (보간·외삽 옵션) |
| 항공 전용 | Quaternion 연산, DCM, 좌표변환, 삼각함수 유틸 |
| 신호 관리 | Delay, Fader (범프리스 전환용), 상태 초기화 인터페이스 |

- Simulink 사용 실적상 기본 블록(Integrator, Sum, Gain, Product, Saturation, Switch, Rate Limiter, Lookup Table, Unit Delay, Memory)이 전체의 절반 이상을 차지 → 이 집합의 구현 품질·검증이 최우선
- **[확정]** 이 집합이 **탑재 C 생성의 단위**다 (M16 codegen). 제어법칙 구조의 정본은 IR이고 블록 구현은 백엔드다 — 블록의 Python `step()`과 C 에미터는 같은 명세의 두 구현이므로 **블록별 등가성 대조로 못박는다**. 이건 §5.5 중복 정의 금지의 예외가 아니라 성격이 다른 것이다: 블록 집합은 **고정·유한(25종)** 이라 대조로 관리되지만, 제어법칙 구조는 계속 바뀌므로 반드시 단일 정본이어야 한다 (MathWorks도 시뮬 엔진과 TLC 템플릿으로 블록을 이중 구현하고 SIL/PIL로 대조한다)
- **[확정]** **이산 계수는 생성 시점에 구워** 파라미터 데이터로 낸다 — 탑재에서 `exp()` 등 libm 호출을 없애 결정론을 확보한다. 계수는 엔진이 `init(dt)`에서 계산한 값을 인스턴스에서 그대로 읽어 굽는다(이산화 공식이 두 번 적히지 않는다). 부작용: **주기(dt)가 형상의 일부**가 되어 지문에 포함되고, 생성 코드에서 dt는 튜닝 가능한 파라미터가 아니라 매크로다 — 값만 고치면 필터 계수가 조용히 틀리기 때문
- **[확정]** 생성은 **결정적**이다(생성 시각 미포함). 산출물을 커밋하므로 "재생성했더니 달라졌다"가 곧 실제 설계 변경이어야 한다
- **[확정]** **모드 분기는 enable 영역으로 표현한다** — 제어법칙에는 "축이 비활성이면 명령필터가 측정을 추적하고 헤딩 적분기를 소거한다"(autopilot.py:147) 같은 상태 부작용이 있어 순수 데이터흐름으로는 표현되지 않는다. Simulink의 Enabled Subsystem과 같은 의미론을 노드 단위로 두고, 같은 enable을 가진 **연속** 노드가 한 영역이 되어 생성 C의 `if/else` 한 덩이가 된다. 최상위의 항법 무효 홀드(law.py:86)는 **그래프 전체의 enable** — 아무것도 실행하지 않고 직전 출력을 그대로 내며 상태도 동결된다
- **[확정]** **제어법칙 구조의 정본은 IR 하나다** (v0.22 이관 완료). `claw/fcl/graphs.py`의 그래프 선언이 구조 그 자체이고, `Autopilot`·`Scas`·`Mixer` 등 클래스는 파라미터를 보유하고 그 그래프를 태우며 원시 항법 상태를 공학량으로 바꿔 주는 **어댑터**다. 설계 실행(Python 백엔드)과 탑재 C(C 백엔드)가 같은 선언에서 나오므로 어긋날 수 없고, "Python과 C를 둘 다 운용할지"는 나중에 정해도 되는 **백엔드 선택**으로 남는다
  - 부수 규칙: 조립된 뒤 **상태는 조립의 러너 한 곳에만** 있다. 자식 인스턴스에 웜스타트를 넣으면 법칙 실행에 반영되지 않으므로 조립에 넣는다(`Scas.reset(states=…)`). 실제로 이걸 어겨 트림 웜스타트가 사라진 적이 있고, 지금은 그 경로가 조용히 무시되는 대신 예외로 터진다
  - 비용은 쟀다: 데모 미션 180 s 폐루프가 11.08 s → 11.37 s (**+2.6%**). 6DOF·공력이 지배적이라 IR 순회 오버헤드는 묻힌다
- **[확정]** **생성 C는 두 축으로 나눈다** — 역할축(`.c` 알고리즘 / `_data.c` 파라미터=rtP / `_types.h` 자료형·dt 매크로 / `.h` 진입점)과 **기능축**(서브시스템별 `{base}_{group}.c`·`.h`). MATLAB의 `File packaging format: Modular` + 서브시스템 `Function packaging: Nonreusable function` · `File name options: Use subsystem name`에 해당한다. 목적은 FCC팀이 **서브시스템 하나만 떼어 읽고 검증**할 수 있게 하는 것이다. 분할 단위는 IR 노드의 이름표(`grouped`)이고 **IR은 평탄한 채로 남는다** — 계층화하면 호출 규약이 IR로 올라와 선언순서·도달성·enable 검사가 전부 계층을 인지해야 하고, "선언 순서 = 실행 순서 = 생성 C 문장 순서"라는 성질을 잃는다. Python 실행기는 이름표를 **아예 읽지 않으므로** 분할이 실행 결과를 바꿀 수 없다
  - 경계를 넘는 신호는 함수 인자가 되며 **이름이 그대로 유지된다** — 정의부 지역변수도, 인자도, 호출부 지역변수도 `ap_theta_out_y`다 (`rtb_Sum_p_idx_1` 류를 만들지 않는다는 요구가 경계에서도 지켜져야 한다)
  - 파라미터·상태 구조체는 **쪼개지 않는다**. 파티션 함수들이 `{base}_params_t`·`{base}_state_t` 포인터를 함께 받으므로 `{base}_reset`과 범프리스 웜스타트 계약이 그대로 남는다
  - enable 영역이 group 경계를 가로지르면 IR이 **거부한다** — `if` 한 덩이가 두 함수에 걸칠 수 없다. 이름표는 연속이어야 하고, 붙일 거면 전부 붙여야 한다(일부만 쪼갠 코드는 "나머지는 어디 있나"를 읽는 사람에게 떠넘긴다)
- **[확정]** **형상 지문은 파일 배치와 무관하다** — 지문은 파라미터·dt·노드 구조의 신원이므로, 어떻게 쪼개든 같은 법칙이면 같은 지문이다(분할 전후 `c0f9af6f848059c4` 유지 확인). 배치 변경은 파일 diff로 보이면 되고, 지문까지 흔들리면 "형상이 바뀐 것인가"를 구별할 수 없게 된다
- **[확정]** **공용 헬퍼는 산출물마다 복제하지 않고 `claw_rt.c`·`.h` 한 벌로** 낸다 (MATLAB `slprj/ert/_sharedutils/` 대응) — 같은 코드를 산출물 수만큼 검증하지 않기 위해서다. 쓰는 것만 내고(안 쓰는 헬퍼는 탑재 코드의 dead code다), 산출물이 여럿이면 **헬퍼 합집합으로 한 번** 만든다. 산출물별로 따로 내면 헬퍼가 적은 쪽이 덮어써 링크가 조용히 깨진다
- **[확정]** **생성 제어법칙의 입력 경계는 "이미 계산된 공학량"** (θ·φ·ψ·p·q·r·V·α·β·h·ḣ·mach)이다. 실기 FCC에서 오일러각·에어데이터·마하는 항법·ADC가 주는 값이고, 손으로 쓴 `law.py:89`·`scas.py:104`가 이를 직접 계산하는 것은 우리 시뮬레이터가 원시 상태(쿼터니언·NED 속도)를 넘기기 때문이다. 그 변환은 생성 코드 밖(통합 계층)에 남는다 — 쿼터니언 연산을 탑재 코드에 넣지 않아도 되고, FCC의 실제 인터페이스와도 맞는다

### 2.3 계층 구조

**[확정]** 최종 형상은 C++ 코어 + Python 해석층 하이브리드. 단, 개발 전략은 **Python 레퍼런스 우선** (모듈 문서 03 §7.1 채택):
- Phase 1~4의 코어(제어 요소·보간·환경·플랜트·법칙 실행부)는 순수 Python(NumPy/SciPy) **레퍼런스 구현**으로 완성. 코어 경계 API를 고정해 두고, 성능이 문제 되는 시점(몬테카를로·배치 규모 확대)에 pybind11 기반 C++ 구현으로 **드롭인 교체**
- Python 레퍼런스판은 폐기하지 않고 C++판의 **회귀 기준(oracle)** 으로 상시 유지 — 이중 구현이 아니라 검증 자산
- **[TBD]** **제어법칙 C 백엔드로의 전환 시점** — 제어법칙 구조가 굳은 뒤로 미룬다. 01 §7 미결 중 엘레본 믹싱 비율·경로추종 알고리즘·모드 전환 조건·저고도 플레어는 **구조를 바꾸는** 항목이고, 공력 DB·작동기 특성·실속 경계가 아직 [기본값] 가정값이다. 굳지 않은 설계를 C로 먼저 쓰면 C를 계속 고치게 된다 — 개발 속도가 아니라 재작업 비용이다. 구조 정본이 IR이므로(§2.2) 이 전환은 다시 쓰기가 아니라 **백엔드 추가**이고, 그래서 미뤄도 부채가 되지 않는다

### 2.4 설계값 연계·정량 영향성 평가

**[확정 — 신규 요구]** 모듈 간 설계값은 유기적으로 연계되며, 어느 단계의 수치 변경이든 전체 출력에 미치는 영향을 정량 평가할 수 있어야 한다.

- **계보(lineage) 추적**: 모든 설계 산출물(트림표, 선형모델, 마진 맵, 시뮬 결과)은 자신이 계산된 파라미터 스냅샷의 **지문(fingerprint)** 을 기록한다 (§5.5 파라미터 계층이 지문 발급)
- **[확정]** 지문 대상 확장: ParamSet뿐 아니라 **입력 데이터 파일(공력 DB, 실속 경계 테이블)의 해시·버전**도 산출물 계보에 기록 — "어떤 DB 버전 + 어떤 파라미터 버전으로 계산됐는지" 재현 가능해야 Simulink 회귀 대조(§7)가 성립
- **설계 파이프라인 DAG**: params → 트림 → 선형화 → 마진 → 시뮬의 산출물 의존 그래프를 관리. 파라미터 변경 시 영향받는 산출물만 자동 무효화·증분 재계산
- **정량 Δ리포트**: 변경 전/후 두 파라미터 스냅샷에 대해 파이프라인을 재실행하고 차이를 정량 비교 — 트림점 이동, 고유치·감쇠비·이득/위상여유 변화, 응답지표(오버슈트·정착시간)·경로오차·실속마진 변화
- **파라미터 스윕/민감도**: 지정 파라미터를 격자로 흔들어 출력 민감도 산출 (배치 실행 재사용)
- 기존 100 vs 50 Hz 마진 비교(§2.3 샘플레이트 원칙)는 이 기능의 특수 사례로 흡수
- **[확정] 영향 매핑은 손으로 적지 않는다** — "이 게인이 저 노드를 건드린다"를 표로 두면
  구조 정본(M16 IR)이 바뀔 때 조용히 낡는다(§5.5 중복 정의 금지가 막는 것이 이것이다).
  파라미터를 흔들어 법칙을 **재조립하고 노드 서명을 diff** 해서 매핑을 유도한다. 부수
  효과로 **구조를 바꾸는 파라미터**도 잡힌다 — `k_thr_turn` 0→ε은 노드 4개를 새로
  만들고(안 쓰이는 경로는 생기지 않으므로) 그건 민감도가 아니라 위상 변경이다
- **[확정] 세 상태를 구분해 보인다** — 같은 "도달"이라도 성격이 다르고, 뭉뚱그리면
  사용자가 "왜 편집해도 안 먹지"를 혼자 알아내야 한다:
  ① **덮임** — 게인 스케줄이 붙은 SCAS 상수는 그래프에 있지만 실행기가 매 스텝 게인
  포트로 덮어쓴다(`inst.step(u, **gains)`) → 구조 diff에는 잡히고 런타임 효과는 0
  ② **미방출** — 스케줄된 `k_rate`는 상수 대신 조회 노드를 쓰므로 그래프에 **없다**
  ③ **법칙 밖** — 항법·작동기·유도는 IR 바깥이라 개루프가 못 본다. "영향 없음"이 아니다
- **[확정] 도달성은 크기가 아니다** — 포화된 가지나 0 게인을 지나는 경로도 도달로 잡힌다.
  「얼마나」는 개루프 Δ(2단)·폐루프 스윕(3단)의 몫이고, 화면이 그 구분을 말해야 한다
- 담당: 모듈 문서(03) M15 `pipeline`

### 3.1 항법(Navigation) 모듈 — 등가 오차 모델

**[확정]** 툴은 EKF를 구현하지 않는다. Navigation 모듈은 실제 항법(EKF) 출력의 **통계적 특성을 재현하는 등가 오차 모델**로 구현한다.

```
항법 출력 = 참값(6DOF) + 오차(백색잡음 + 상관잡음/바이어스) + 지연
```

**근거**
- 툴이 EKF를 구현해도 실제 비행할 항법팀의 EKF와는 다른 근사물 → 현실성 착시만 유발
- 등가 오차 모델은 실제 EKF의 **성능 수치**(공분산, 지연)를 그대로 반영 가능 → 재구현보다 실제에 근접
- 제어루프가 느끼는 것은 제어대역 대비 빠른 잡음과 느린 바이어스뿐이며, 추정기 내부 구조는 제어기 설계에 영향 없음
- 항법은 별도 전문 영역 — 중복 개발 회피

**인터페이스 개방**: Navigation 모듈은 교체 가능 컴포넌트(레지스트리, §2.3)로 등록하여, 추후 항법팀의 실제 EKF 모델이나 비행소프트웨어 코드를 그대로 꽂을 수 있게 한다.

**오차 모델 파라미터** (상태별로 정의)
| 항목 | 내용 |
|---|---|
| 백색잡음 | 표준편차 (위치/속도/자세/각속도별) — **위치·속도는 수평(N·E)/수직(D) 분리** (01 §2.5 [기본값]) |
| 바이어스 | 초기 바이어스 + 상관시간(1차 마르코프) — 위치축, **수평/수직 분리** |
| 지연 | 항법 출력 지연 (transport delay) |
| 갱신주기 | 항법해 출력 주기 |

**[기본값]** 초기값은 GPS/INS 통합항법의 일반적 수준으로 시작한다. 항법팀의 실측·공분산 해석 자료 확보 시 대체.
- 위치: 수 m 급 (수평/수직 구분)
- 속도: 0.1~0.5 m/s 급
- 자세(롤·피치): 0.1° 내외 / 방위: 롤·피치 대비 큼
- 지연: 수십 ms 급
- 갱신주기: 제어주기(100 Hz)와 동등하거나 낮음 → 멀티레이트 처리 필요
- **[TBD]** 구체 수치는 항법팀 자료 확보 시 확정. 위 값들은 자리표시자(placeholder)

## 4. 웹 UI

**[확정]** UI는 웹 기반. Simulink식 자유 블록 배선 에디터는 **만들지 않는다** — 제어 아키텍처는 고정이므로 웹은 파라미터·옵션·데이터 편집과 결과 열람의 얼굴.

편집 수준 **[확정]** (a)+(b), (c)는 제외:
- (a) 파라미터·게인·트림 케이스·웨이포인트 편집 + 고정 구조 신호흐름 시각화
- (b) 제한된 컴포넌트 교체 (레지스트리 등록 대안 중 선택)

**[확정]** 진입 UI는 **블록 다이어그램 허브** (Simulink "다이어그램에서 시작" 대응): 고정 구조 신호흐름 다이어그램(SVG — 설계 순서 ①~⑤ 중첩 점선 프레임, 게인 스케줄 점선 배선, 항법 피드백 경로 포함)이 첫 화면이고, 블록·프레임 라벨 클릭 → **서브시스템 하위 페이지**(#blocks/<id> — Simulink 서브시스템 더블클릭 대응, 브라우저 뒤로가기로 상위 복귀): 브레드크럼 + 내부 블록도(포트·합산점·이득 경로 — 엔진 구현과 1:1. 표기는 2계층: **코드에 대응하는 요소만 그 설계 단계 색의 틴트**로 칠하고 `data-code`가 engine/claw 파일:심볼을 지목한다(테스트가 실존을 검증), 이해를 돕는 설명 요소는 무채색 점선(`nblk`)으로만 허용 — MathWorks식 출력 병기 등. 자유 배선 없음은 유지) + 설계 노트([확정]/[기본값]/[TBD] 칩 — fcs-context 태그와 동일 의미) + 파라미터 패널. 파라미터 패널: ① 레지스트리 스키마 폼/열람 표(§2.3 폼 자동 생성 — 단위·범위·기본값, 파라미터 보유 법칙 컴포넌트 Autopilot·ScasAxis·Mixer를 레지스트리 "fcl" 카테고리에 등재) ② 정본 편집 화면 이동(게인 스케줄·SCAS→게인 탭, 미션플래너·유도·작동기·항법→시뮬 탭, α 리미터→엔벨로프 탭, 플랜트→트림 탭). 폼 편집(시뮬 주입)은 **주입 경로가 있는 블록만** 허용 — 현재 오토파일럿(전체 kwargs 교체, 시뮬 탭 '편집 AP') — 진실 이원화 방지. 캠페인 단위 작업(트림 격자·마진 맵·미션 실행)은 탭 유지.

CSP(`default-src 'self'`)와 eval-free 방침 때문에 하이라이터를 반입할 수 없어 `lib/highlight.js`가 직접 훑는다: **무손실이 계약**이다(`tokenize(code).map(t => t.s).join("") === code`) — 색칠은 표시이고, 표시가 코드를 한 글자라도 바꾸면 그건 색칠이 아니라 위조다(그 코드는 복사돼 빌드로 들어간다). 파서가 아니라 문맥 없는 스캐너라 안 닫힌 주석·따옴표에서 **뒤를 잃지 않는 쪽**으로 실패한다. 거터는 본문과 같은 줄 수를 보장하려고 본문을 절대 줄바꿈하지 않고(넘치면 가로 스크롤, 거터는 sticky), 20만 자를 넘는 파일은 색 없이 낸다(그 사실을 화면이 말한다). 종류·대상·형식·파일 탭은 **전부 코드 위에 남는다** — 서랍에 넣으면 화면의 코드가 어느 형상의 것인지 알 수 없게 된다. **어두운 것은 코드판뿐이고 페이지는 밝다**(v0.54, 사용자 요청) — 처음엔 탭 전체에 다크 스킨을 입혔는데 다른 탭과 나란히 보면 이 탭만 페이지째 뒤집혀 보인다. 어두워야 하는 것은 편집기이지 탭이 아니고, 블록도 하위 페이지의 코드 패널이 이미 같은 모습이다(밝은 페이지 위의 VS Code 판). 다크 탭은 이제 영향성·가상환경 둘뿐이다 — 둘은 **주 그림 자체가** 검은 캔버스다

담당 기능 (**[확정]** 전부 웹):
- **[확정] 엔벨로프 탭**(`#envelope`, v0.38; **6계층 재편 v0.53**) — 제어법칙 설계 엔벨로프(01 §2.6)의 얼굴.
  - **[확정] Envelope는 하나가 아니다 — 목적에 따라 여섯 층이고, 그 순서가 곧 설계 순서다** (v0.53, 사용자 제시 분류). 종전에는 패널 다섯 장(합성 M-h·V-n·공력·추진·운용)이 **나란한 그림 다섯**으로 서 있었다. 그 배치는 어느 것이 상위 제약이고 어느 것이 그 제약에서 파생된 결과인지를 말하지 않는다 — V-n은 구조 한계 하나일 뿐인데 합성 선도와 같은 무게로 놓여 있었다. 지금 서랍은 기능 묶음이 아니라 **파이프라인**이다: ① 운용·비행(Flight Envelope — 축은 (M,h)로 그리지만 실제 운용점은 `x_op = [M, h, W, CG, 형상]` 다차원) → ② 트림(각 점이 실제로 trim되나 · α_trim·δe_trim·T_trim, 공력 DB와 안정·조종 미계수가 여기서 쓰인다) → ③ 선형 모델(`ẋ = A_i x + B_i u`와 모드 ω_n·ζ) → ④ 제어 설계·스케줄링(대표 설계점 선정 + `K = f(M, q̄)` 배치, LPV면 ρ) → ⑤ 한계·보호(V-n·V_S/V_A/V_NO/V_D·n_z·q̄ → 제어법칙의 Envelope Protection이 여기서 나온다. 조종권 한계도 같은 층) → ⑥ 검증·마진(설계점 **사이**까지 촘촘히 sweep한 GM/PM·ζ/ω_n 맵). ①이 전면 무대(합성 M-h 캔버스)이고 나머지는 칩이다
  - **이 탭이 계산하지 않는 층도 층으로 세운다.** ③·⑥의 수치는 마진 맵 탭이 낸다 — 그렇다고 목록에서 빼면 파이프라인에 구멍이 뚫린 채 "엔벨로프는 다섯 층"이라고 말하게 된다. 그 서랍은 **그 층이 무엇이고 어디서 나오는지**와 지금 저장된 산출물이 몇 건인지(`/results` 종류별)를 낸다. 없는 그림을 지어내지 않는 것과 층이 없는 척하는 것은 다르다. 못 물어봤으면 0건이라고 하지 않는다
  - **⑥은 ④와 격자가 달라야 한다**는 것이 이 층을 따로 두는 이유다 — 게인을 마하 몇 점에서 설계했더라도 검증은 그 사이를 훨씬 촘촘히 훑어야 스케줄 경계점 사이에서 마진이 꺼지는 곳을 찾는다. 마진 맵 탭의 격자 서랍이 같은 문장을 반복해 두 탭이 갈리지 않게 한다
  - ①의 서랍은 **경계 귀속을 고도 구간별로** 접어 낸다(41행을 그대로 내면 표가 아니라 목록이다 — 귀속이 바뀌는 지점에서만 행을 낸다). 그리고 이 도구가 축으로 **쓰지 않는 것**(CG·형상)을 명기한다: 실기체로 갈 때 이 층이 가장 먼저 넓어지는 자리이고, 그때 아래 층 전부가 축 하나씩을 더 받는다

  다섯 장이 세로로 쌓여 그래프가 그중 한 칸이었고 첫 화면에서 표 넷이 동시에
  펼쳐져 있었다. 지금은 그래프가 페이지 위에 그대로 놓이고(이 탭만 `main`
  max-width 1580 · 캔버스 논리폭 1500), 파라미터 표·진단·개루프·스윕은 칩을 눌러야
  열린다 — **한 번에 하나**만(둘을 동시에 열면 그냥 다시 쌓기다). 칩에 개수 배지를
  달아 서랍이 닫혀 있어도 결과가 생긴 것이 보이고, 경고 칩은 경고가 **있을 때만**
  선다(0을 세는 칩은 경고가 생긴 사실을 가린다). 범례는 서랍에 넣지 않는다 —
  색이 칠해진 그래프가 늘 떠 있는데 범례를 클릭 뒤로 숨기면 화면이 자기 문법을
  설명하지 않게 된다.
  **잡 상태는 서랍 밖에 산다** (v0.50) — 스캔·개루프·스윕은 셋 다 **진단 서랍의
  버튼**에서 출발하는데 결과는 다른 서랍에 산다. 한 번에 하나만 열리므로 진행률·실패를
  결과 서랍에만 쓰면 사용자가 방금 누른 화면에서는 아무것도 안 보인다. 서랍 밖 한
  줄이 진행률을 말하고, 끝나면 결과가 있는 서랍을 **열어 준다** — 결과를 찾아 헤매게
  하지 않는다.
  **[확정] 정량 판독대 — 「얼마에서 얼마로」** (v0.49) — 그래프 바로 아래에서,
  고른 파라미터 하나에 대해 세 단이 각각 한 줄씩 `기준 → 섭동`을 큰 숫자로 낸다.
  종전 화면은 세 단이 전부 Δ만 냈고(2단은 기준과 Δ가 다른 열이라 눈으로 더해야
  했다) "48.3°에서 47.1°로"라는 문장이 화면 어디에도 없었다 — 재는 값은 셋 다 서버가
  이미 주던 것이라(`base`·`perturbed`, base 런의 `metrics`) 짝짓기만 웹이 한다.
  없는 단은 빈칸이 아니라 **사유**이고, 그 사유는 셋으로 갈린다: "아직 안 쟀다" ·
  "쟀는데 이 손잡이가 대상이 아니었다"(처방 부분공간만 흔들므로 흔한 일이다) ·
  "재 봤는데 유효한 Δ가 없다". 뭉치면 화면이 방금 돌린 계산을 다시 돌리라고 시키고,
  다시 돌려도 문구가 안 바뀐다.
  **표시 규칙 다섯이 이 판독대의 전제**이고 전부 라이브·리뷰에서 잡혔다:
  ① 자릿수는 두 값이 갈릴 때까지 늘린다(`fmtPair`) — 고정 자릿수면 1% 섭동이
  「4.0e−4 → 4.0e−4」로 뭉개져 화면이 "안 변했다"고 말한다 ② 자릿수는 **열마다
  하나**다(`columnFormat`) — 행별 최소의 최댓값이 아니다: 자릿수를 올리면 반올림
  경계가 옮겨 가 낮은 자릿수에서 갈리던 쌍이 새로 뭉개진다(40.847→40.853이 3자리
  40.8/40.9에서 4자리 40.85/40.85로) ③ 그 탐색에서 **어느 자릿수로도 못 갈리는 행은
  뺀다** (v0.50) — 빼지 않으면 차이가 7자리 밑인 행 하나가 열 전체를 7자리로
  끌어올리는데 정작 그 행은 7자리로도 안 갈린다: 아무도 못 얻는 정밀도를 위해
  나머지가 전부 거짓 정밀도를 뒤집어쓴다 ④ **지수/소수 표기도 열마다 하나**다
  (v0.50) — 자릿수만 통일하면 같은 base 런의 0.00105가 어떤 행에서는 `1.05e-3`,
  기준 행에서는 `0.00105`로 찍혀 ②가 막으려던 것이 표기로 되살아난다
  ⑤ 비율이 0.1% 미만이면 「+0.0%」로 반올림돼 같은 거짓말을 하므로 절대 Δ로
  말한다(`fmtChange`). 지표 12개 중 무엇을 먼저 보일지는 `impactRank`가 정한다 —
  Δ가 0이면 맨 뒤, 기준이 0인데 움직였으면 맨 앞(없던 일이 생긴 것은 비율로
  표현되지 않지만 질적 변화다). 정렬은 `byImpact`로 한다: 0에서 벗어난 지표가 둘이면
  `Infinity − Infinity`가 NaN이라 뺄셈 비교자는 계약이 깨진다.
  **저장된 2·3단 수치에는 지문을 대조한다** (v0.50) — 결과는 모듈 스코프라 탭을
  떠났다 와도 살아 있는데 그 사이 게인 탭에서 값을 바꾸면 형상이 달라진다. 그때
  옛 수치를 그냥 띄우면 화면에 없는 기체의 마진·지표를 지금 것으로 읽게 되므로,
  지문이 어긋나면 수치보다 그 사실을 먼저 말한다(지문이 계보로 있는 이유가 §2.4다).
  **표가 정본 표면이고 캔버스는 보조다** — 캔버스는 보조기술에 불투명하므로 화면이
  말하는 모든 사실(상태·도달 개수·도달 출력)이 파라미터 표에 그대로 있다(지도
  편집기가 웨이포인트 표에 접근성을 맡긴 것과 같은 규약). 서랍에 넣었어도 표는
  그대로이고 칩 하나로 열린다.
  **[확정] 2·3단은 케이스 격자가 단위다** (v0.29) — 마진 맵과 같은 격자 입력(mach
  범위 × 고도·연료 목록, 기본 15케이스). 2단(개루프 Δ)은 케이스당 ~10 ms라 격자
  전체로 돌고, 화면은 (손잡이×루프) 최악 Δ와 그 케이스를 요약 정본으로, 케이스별
  전체 표를 접힌 근거로 둔다. 3단은 케이스 × 런 비용이 곱이라 두 단계다:
  **A 전 케이스 스캔**(`POST /influence/scan`)이 케이스마다 base 런 하나로 지표를
  재고(`sweep_plan(shape, [], ())` = base 계획 — run_sweep 그대로 재사용)
  `diagnose_grid`(규칙 4 — "격자 런이 생기면 소급 활성화되는 별도 입력"이라던 그
  함수)가 지표별 정상/국소/전역과 결함 케이스를 판정한다 → **B 부분 풀 스윕**(기존
  `/influence/sweep`)은 스캔이 고른 결함 케이스(체크박스로 조정)에만 처방 부분공간을
  흔든다. 케이스 이름은 웹이 명시 부여한다 — 판정의 bad_cases(이름 문자열)를 B의
  케이스 객체로 되돌리는 매핑이 서버 자동 명명 형식에 묶이지 않게. 영향성 라우트의
  케이스 상한 200은 서버 검증이다(오타 격자가 단일 워커를 시간 단위로 점유하지 않게)
  **[확정] 3단 C — 구간 경향: 「전 구간에서 어느 쪽으로」** (v0.52) — B가 답하지
  못하던 질문의 자리다. B의 요약 표는 런별 **최악 한 칸**만 내고(어디가 제일 나쁜지는
  알지만 엔벨로프를 따라 어느 쪽으로 기우는지는 모른다), 케이스×런 전체 표는 사실을
  다 갖고도 15케이스 × 9런 = 135행이라 경향이 행 사이에 흩어져 사람이 눈으로 피벗해야
  했다. C는 그 135행을 손잡이 하나 기준 **(구간 × 지표) 한 장**으로 접는다 — 행이
  구간이라 세로로 한 번 훑으면 "이 게인을 올리면 저고도에서만 좋아지고 고고도에서는
  나빠진다"가 그대로 읽힌다. **새 잡도 새 엔드포인트도 없다**: B가 이미 돈 런을
  다시 세우는 순수 변환(`lib/influence.js` `trendMatrix`)이라 서랍을 열면 즉시 뜬다.
  네 가지 규칙이 이 표의 전제다: ① **단조 판정은 연속 차분의 부호**로 한다 — 회귀
  기울기의 부호로 하면 −20%에서 튀고 +20%에서 돌아오는 곡선이 "단조"로 접혀 스팬
  안에 극점이 있다는 사실(= 이 손잡이를 한쪽으로 밀면 안 된다)이 사라진다
  ② **색은 방향이 아니라 좋고 나쁨**이다 — 같은 ↑가 실속마진에서는 개선이고 추종
  RMS에서는 악화라, 극성은 서버 선언(`MetricDef.better`)이 정본이고 선언이 없으면
  중립 잉크로 **판단하지 않는다**. 기호(↑↓∿=—)가 색과 별도로 경향을 말한다(색만이면
  색각 이상·흑백에서 표가 무의미해진다) ③ **평탄의 기울기는 정확히 0**이고 단조 판정
  자체에도 상대 문턱(1e−12)이 선다 — 회귀식에 맡기면 값이 전부 같아도 평균 뺄셈의
  반올림이 남아 `7.7e−34`가 나오고(실측), 부호만 보면 1 ulp 차이에 「비단조」가 서서
  **이 표에서 가장 센 판정이 부동소수 끝자리로** 나온다 ④ **행 순서는 격자 순**(fuel,
  alt, mach)이다
  — 실행 순서인 서펜타인은 인접 트림 시드용이라 표에서 마하가 줄마다 뒤집힌다
  (`lib/grid.js` `orderCaseNames`가 `nameCases`의 역함수를 쥔다; 이름 하나라도 못 읽으면
  **전부** 원래 순서 — 절반 정렬은 비일관 비교자다). 전 구간에서 값이 없는 지표는
  「—」 열로 표를 채우지 않고 이름으로 따로 낸다(표준 진단 기동에는 접지도
  웨이포인트도 없다 — 없는 지표가 아니라 이 기동이 못 재는 지표다). **∞는 그 목록이
  아니다** — 곡선에는 못 세우지만(차분이 ±∞·NaN) 발산한 런이 정확히 그 자리라, 칸은
  서버가 준 값 그대로 ∞를 찍고 사유도 "재지 못했다"가 아니라 "발산한 런의 자리"라고
  말한다(같은 행의 「발산」 배지와 어긋나지 않게). 이 표의 구간은
  **스윕이 실제로 돈 케이스뿐**이고 화면이 그렇게 말한다: A로 좁혔으면 격자 전체가
  아니다

- **[확정]** **단독 사용자, 로컬 서버**. 다중 사용자·인증·동시 작업 큐·편집 충돌 처리 스코프 제외 (추후 확장 여지)

- **지도 타일**: 폐쇄망에서 인터넷 타일(OSM 등) 불가 → 오프라인 타일 서버 반입 또는 위경도 격자+해안선 벡터 폴백 모드를 처음부터 설계. **측지 원점이 그 전제다** — NED 평면이 지구 어디에 놓였는지 모르면 타일도 지형도 붙일 수 없다(`SimRunIn.origin` → `meta.origin`, 엔진은 보지 않는 등록 정보). 변환은 `claw.env.geodesy`가 정본이고 웹 `lib/geo.js`가 사본인데, 프레임마다 계산해야 해서 서버 왕복이 불가능하기 때문이다 — 그 중복은 `data/geodesy-fixture.json`을 양쪽 테스트가 **같이 읽어** 묶는다.
- **[확정]** 프론트엔드 스택: **순수 바닐라 ES 모듈 + no-build**, 외부 의존은 **아래 예외 1건**을 빼고 0 — 근거: ① 폐쇄망 반입물 = `web/` 파일 전부, 현지 수정이 텍스트 에디터로 가능(빌드 툴체인 반입 불요) ② eval-free — 엄격 CSP(unsafe-eval 금지) 환경에서도 동작(런타임 템플릿 컴파일 프레임워크 배제 사유) ③ 반입 심사 가능한 비-미니파이드 소스. 플롯은 자체 Canvas. 서버(FastAPI StaticFiles)가 정적 서빙 — 서버 1대 = 배포 전체
- **[확정]** 예외 1건: **3D 월드 렌더링에 한해 vendored ESM 단일 라이브러리**(three.js, `web/js/vendor/three/`). 근거: 원근·깊이·조명·톤매핑을 갖춘 실사 3D를 자체 WebGL2로 쓰면 수천 줄이고 **그 코드가 곧 반입 심사 surface**가 된다 — 검증된 소스 하나가 심사도 교체도 더 쉽다. 위 ①②③은 그대로 유지된다: CDN이 아니라 `web/` 아래 파일이라 반입물 정의가 바뀌지 않고, 빌드 단계가 없으며(모듈이 형제 파일을 상대 import), `eval`·`new Function` 0건을 반입 시 실측해 `VERSION`에 기록한다(버전을 올릴 때마다 재확인). 애드온(`examples/jsm/`)은 반입하지 않는다 — 하나 들이면 그것이 또 상대 import를 물어 반입물이 계속 는다.
- **[개정 2026-09-02]** 위 예외를 가상환경 재설계가 대체했다. three는 반입본이 아니라 `web/world/`의 **npm devDependency**(개발 머신 전용)이고, 반입물은 **커밋된 빌드 산출물** `web/world/build/world.js` 하나다(비-미니파이드 ESM, eval-free는 CSP `default-src 'self'`가 계속 강제). `examples/jsm/` 애드온(GLTFLoader·EffectComposer 계열)은 **전면 허용**으로 바뀌었다 — 산출물에 트리셰이킹되어 들어오므로 "상대 import가 반입물을 불린다"는 반대 근거가 사라졌기 때문이다. 반입본 `web/js/vendor/three/`(2.0 MB)는 걷어냈다. 빌드 툴체인(Node)은 반입하지 않는다 — far side에서 산출물을 고칠 일이 생기면 그것은 재반입 사유다.
- **[확정]** 그 예외의 대가로 **렌더러 경계를 인터페이스로 가른다**: 경계를 넘는 값은 전부 NED·m·rad이고, 카메라 pose·자세·형상 생성·재생 커서 같은 판단은 `lib/`의 순수 함수에 두어 테스트한다(`views/worldrenderer.js`가 계약, `views/renderer-three.js`가 구현). 어댑터가 three에서 import하는 심볼 목록이 곧 자체 WebGL2 구현이 채워야 할 표면이며 그 파일 상단 주석이 관리한다. **교체가 희망이 아니라 규약이어야 예외가 정당화된다.**
- **[개정 2026-09-02]** 렌더러 **교체 가능성 규약은 은퇴**했다 — 애드온을 전면 허용하면서 GLTF 로딩·후처리를 자체 WebGL2로 다시 쓰는 교체는 현실성이 없어졌고, `worldrenderer.js`·`renderer-three.js`는 삭제됐다. 남긴 것은 교체가 아니라 **계층**이다: 판단(자세·카메라·해수면·파동·타면·발사관·해안 거리장)은 `web/world/src/core/`의 순수 함수 + 공존 테스트에 있고, three를 아는 층은 `scene/`·`shaders/`·`post/`로 얇게 유지한다(`web/world/src/scene/axes.ts` 머리말이 이 판단의 정본).
- **[기본값]** 웹 테스트 전략: 로직 모듈은 공존 `*.test.js`를 node 내장 러너(`node --test`, npm 의존 0)로 — **개발 환경 전용 도구**(반입물 아님). DOM 조립 전용 모듈은 얇게 유지하고 실서버 데모로 검증

- 요구사항:
  - 단일 정의 원본에서 C++ 코어 / Python 해석층 / 웹 UI가 모두 참조 (중복 정의 금지)
  - 단위·설명·유효범위를 메타데이터로 보유 → 웹 UI 폼 자동 생성 및 입력 검증에 활용
  - 연료 소모에 따른 질량·CG·관성 변화는 시간·상태 의존 파라미터로 취급
  - 텍스트 기반 파일로 저장하여 버전관리(diff) 가능
- **[확정]** "중복 정의 금지"의 집행 규칙 — **웹은 엔진 기본값을 재기술하지 않는다**: 요청에 사용자가 실제로 정한 값만 싣고 나머지는 엔진 ParamDef가 채우게 한다(부분 지정 보충). 화면에 즉시 값을 보여야 해서 폴백 사본이 불가피한 경우(폼 프리필)는 레지스트리 스키마가 도착하면 사용자가 손대지 않은 값만 갱신해 스스로 정렬한다. 근거: 시뮬 탭이 항법 기본값 9개를 재기술해 그중 7개가 엔진과 어긋난 채(pos_std 1.0↔3.0, update_hz 50↔100 등) 돌던 사례 — 블록도는 엔진 값을 표시하는데 실행은 다른 값이라 무증상이었다 (v0.18)
- **[확정]** 파일 포맷 YAML + JSON 스키마 (§5.4와 동일 규격). 파라미터 스냅샷마다 **지문(fingerprint)** 발급 — 산출물 계보 추적·영향성 평가(§2.4)의 키
- 합격기준을 파라미터로 관리하면 판정 기준이 지문에 포함됨 — 산출물 계보에 요구도 버전이 자동 반영되고, 기준 변경 시 Δ리포트(§2.4)로 판정 변화 추적 가능

## 8. 사용자 워크플로우

**[확정]** 주 인터페이스는 웹 UI. 모든 단계는 CLI/Python API로도 수행 가능(엔진 우선 원칙).

1. 공력 DB(CSV/Excel) + 실속 경계 테이블 + 기체 파라미터 로드 → DB 뷰어로 이상 검사
2. 웹에서 트림 케이스 매트릭스 정의 → 배치 트림(진행률 모니터링) → 결과표·플롯
3. 트림점별 선형화 → 안정성·마진 맵 대시보드
4. 게인 스케줄 설계 — 웹에서 **스케줄 자리 선택**(형상) 후 테이블 값 편집
5. 지도에서 웨이포인트 임무프로파일 편집 → 폐루프 시뮬 → 재생 + 엔벨로프 감시
6. 검증 리포트 생성·열람 (벤치마크/회귀 비교 포함)
