## 1. 분할 원칙

- **[확정]** 엔진 우선 (구현 문서 §2.3) — 모든 모듈은 Python API/CLI로 완결. server/web은 동일
  API의 소비자일 뿐, 엔진 개발을 막지 않는다
- **[확정]** 모듈 = **독립 개발·독립 검증 단위**. 모듈 간 결합은 §4의 인터페이스 계약(데이터
  구조)으로만 — 나중에 합치는 작업이 "인터페이스 맞추기"가 아니라 "이미 맞는 것 조립"이 되도록
- **[확정]** 계층 규칙: 상위 계층은 하위 계층만 의존. 같은 계층 간 상호 의존 금지.
  조립(플랜트+법칙+항법 연결)은 sim 모듈이 담당 (composition root)
- **[확정]** **코어 경계 명시**: blocks·tables·env·plant + 법칙 실행부는 "코어"로 묶고 API를
  고정 — 추후 C++(pybind11) 구현으로 교체 가능한 경계 (§7.1 언어 전략 참조)
- **[확정]** 교체 가능 컴포넌트(경로추종 알고리즘, 항법 모델, 적분기 등)는 레지스트리+파라미터
  스키마 원칙(구현 문서 §2.3)을 따른다
- **[확정]** **설계값 연계·영향성 평가** (구현 문서 §2.4): 모든 산출물 계약은 자신이 계산된
  파라미터 지문(lineage)을 보유하고, 산출물 의존 DAG(M15 pipeline)가 변경 전파·정량
  Δ리포트·민감도 스윕을 담당한다

## 2. 계층 구조

```
[L5 인터페이스]   web ──────► server (FastAPI)
                                │  (엔진 Python API만 호출)
[L4 해석·실행]   trim │ analysis │ sim │ verify │ pipeline(영향성)
[L3 법칙]        fcl (SCAS·오토파일럿·믹싱·α리미터) │ guidance (경로·모드 실행기)
[L2 모델]        plant (6DOF·공력·추진·작동기·센서) │ nav (등가 오차 모델)
[L1 수치 코어]   blocks (제어 요소) │ tables (보간·공력DB) │ env (대기·지구)
[L0 기반]        common (규약·좌표·쿼터니언) │ params (파라미터·레지스트리·스키마)
```

## 3. 모듈 정의

구현 문서 §3의 기능 6모듈(Flight Control, Guidance, Navigation, Actuator, Sensor, Aircraft
Dynamics)은 아래 M5~M8에 대응된다 (Actuator·Sensor는 plant의 서브패키지).

아래 표는 번호 순이지만 **모듈 상세는 엔진(M0~M12 · M15~M17) → 인터페이스(M13 · M14) 순**으로

### M0 `common` — 기반 규약

- 좌표계(동체축, NED)·단위계·부호 규약의 **코드 구현체**. `conventions.md`(도메인 문서 §6)
  확정과 동시 작성 — 전 모듈이 이것만 참조
- 쿼터니언/DCM/오일러 변환, 좌표변환(NED↔동체↔WGS-84), 단위 변환 유틸
- 의존: 없음. 검증: 변환 왕복 일치, 참조값 대조 단위테스트

### M1 `params` — 파라미터 관리 + 레지스트리

- 단일 정의 원본(텍스트 파일, diff 가능)에서 게인·기하·질량/관성·리미터 값 관리.
  단위·설명·유효범위 메타데이터 → UI 폼 자동 생성·입력 검증의 원천
- 연료 소모에 따른 질량·CG·관성 변화는 상태 의존 파라미터로 취급
- 컴포넌트 레지스트리: 교체 가능 컴포넌트의 등록·조회 + 파라미터 JSON 스키마 노출
- **[확정]** 파일 포맷 **YAML + JSON 스키마** — 웹 편집과 파일 편집이 같은 스키마를 공유한다
  (02 §5.4 · 02 §5.5)
- 의존: M0

### M2 `blocks` — 제어 요소 라이브러리

- 구현 문서 §2.2 전체 목록: Gain/Sum/Integrator(안티와인드업·초기화)/필터(Lag, Lead-Lag,
  Washout, Notch…)/PID(게인 스케줄 가능)/Saturation/Rate Limiter/Backlash/Fader 등
- 공통 프로토콜: `init(dt)` → `step(u) → y` → `reset(state)`. 이산화 계수는 주기로부터 자동 계산
  (샘플레이트 파라미터화 원칙, 02 §2.3)
- Simulink 사용 빈도 상위 기본 블록(Integrator, Sum, Gain, Saturation, Switch, Rate Limiter,
  Lookup, Unit Delay)이 **최우선 품질 목표** — 블록별 해석해/Simulink 참조값 대조 단위테스트
- **탑재 C 생성의 단위** — 블록마다 C 에미터를 갖는다(M16 `emit_c`). Python `step()`과 C
  에미터는 같은 명세의 두 구현이므로 **블록별 등가성 대조가 필수**이며, 이산 계수는 에미터가
  다시 계산하지 않고 `init(dt)`를 태운 인스턴스에서 읽어 굽는다(공식이 두 번 적히지 않게)
- 의존: M0, M1(스키마 등록). C 에미터 소비자는 M16

### M3 `tables` — 보간·데이터

- 1D/2D/nD Lookup(보간·외삽 옵션), 공력 DB 로더(CSV/Excel→pandas→내부 포맷), 실속 경계
  테이블(공력팀 정본), DB 유효범위 질의(엔벨로프 플래그의 근거), DB 뷰어용 슬라이스 추출(CL–α
  곡선 등)
- **[TBD]** 보간 방식·외삽 정책·테이블 규격 (02 §5.1 · 02 §5.3)
- 의존: M0

### M4 `env` — 환경 모델

- ISA 표준대기, 중력, WGS-84 지구모델. 바람/난류(Dryden)는 확장 항목
- 의존: M0. 검증: 표준대기표 대조

### M5 `plant` — 비행체 모델

- 서브패키지: `eom`(6DOF 운동방정식+적분기), `aero`(공력, M3 소비), `prop`(프로펠러 추력 T =
  δσ·min(T_static, ηP/V) — 단발 중심선이 정본, 상수추력·쌍발도 레지스트리 선택 가능: 01 §2.1
  개정 · 01 §2.4), `mass`(연료 의존 질량·CG·관성), `ground`(스키드 접촉·발사 레일 — 01 §3.3.1),
  `actuator`(2차계 가정값 시작, rate/position limit·backlash), `sensor`(초기 이상센서 →
  노이즈·지연)
- `ground`는 **힘과 구속 둘 다** 낸다: 스키드 접촉은 `aircraft.fm`의 네 번째 항(공력+추진+중력에
  이어)이고, 발사 레일은 힘이 아니라 구속이라 sim이 별도 경로로 적분한다(등가속 해석해). 접촉은
  불연속 대신 스프링-댐퍼 연속 근사 — RK4가 스텝당 힘을 4번 평가하므로 h=0에서 끊기는 힘은
  부단계가 지면 안팎을 오가며 적분 차수를 무너뜨린다. `Aircraft(ground=None)`이 기본이라 미장착
  경로는 도입 전과 완전히 동일하다
- 서브패키지 단위로 독립 개발 가능 — 각각이 구현 문서 §3의 모듈 4·5·6
- 의존: M0, M1, M3, M4. 검증: 물리검증(에너지 보존, 스텝 반분 수렴 차수) + F-16 공개 모델
- **[기본값]** 1차 대상은 도메인 문서의 델타윙 고정익. 비행체 프로파일(공력DB+파라미터+법칙
  템플릿) 교체로 타 기체 수용 (§7.2)

### M6 `nav` — 항법 등가 오차 모델

- 참값(plant) + 백색잡음 + 1차 마르코프 바이어스 + 지연 + 갱신주기 (02 §3.1). EKF 미구현
- 레지스트리 등록 컴포넌트 — 추후 항법팀 실제 EKF/비행SW 코드로 교체 가능
- **핵심 계약: 법칙(M7·M8)은 절대 plant 참값을 직접 보지 않고 `NavOutput`만 소비** — 이 경계가
  항법 강건성 평가를 가능케 함
- 의존: M0, M1, M2(잡음·지연 블록)

### M7 `fcl` — 비행제어법칙

- SCAS(피치/롤/요 PI, 러더 워시아웃), 오토파일럿(속도/고도/헤딩 PI, 차동추력 보상, 선회 시
  엘리베이터/스로틀 피드포워드), 게인 스케줄(Mach·고도·연료 테이블), α 리미터(실속 경계 − 마진),
  엘레본 믹싱[제어 할당](엘레본4 믹싱 행렬 + 러더 + 스로틀2)
- M2 블록의 조립으로 표현 — **구조의 정본은 `fcl/graphs.py`의 IR 선언 하나**이고, 클래스들은
  파라미터 보유 + 그래프 실행 + 원시 항법→공학량 변환을 맡는 어댑터다 (07 §1, M16). 탑재 C도
  같은 선언에서 나온다. 조립 후 상태는 조립의 러너 한 곳에만 둔다
- 고정 아키텍처(01 §3) — 자유 배선 없음. 멀티레이트 입력(항법 주기 ≠ 제어 주기) 전제
- **스케줄 자리의 정본은 `graphs.py` SCHEDULABLE 한 표**(그룹 → 허용 키, 16자리 — 01 §3.4).
  `autopilot_nodes`의 거부, `law.py` 조립 검증, 서버 `/gains/catalog`가 전부 이 표를 읽는다.
  자리 → 설계점 상수 대응은 `schedule.py::design_gains`이고 AP 축의 이름 차이(`alt.k_rate` =
  `k_hdot` 등)를 여기서 흡수한다 — 이 표는 그래프가 실제로 방출한 상수와 대조하는 테스트로 낡지
  않게 못박는다. `make_demo_gain_tables(names)`가 임의 자리의 테이블을 같은 동압 스케일
  **법칙**으로 만든다 — **상한만 축별**이고(피치·미측정 2.0, 롤 4.0 — v0.74, 01 §3.4) 새로 켜는
  자리는 기본 상한을 따르므로 켜기 전후 비교는 그대로 성립한다
- 의존: M0~M4 (env는 스케줄 변수 마하 산출용 — L3→L1 계층 규칙 내). 검증: 선형모델 상 루프별
  응답, 이후 폐루프 sim

### M8 `guidance` — 유도

- 웨이포인트 열 → 경로 생성 → 경로추종(알고리즘은 레지스트리 교체: LOS/L1/벡터필드 **[TBD]**),
  출력은 속도/고도/헤딩 명령. 웨이포인트는 `(n, e)` 또는 `(n, e, alt)`이고 `LosPath.step`은
  `(heading, alt, done)`을 낸다 — 고도는 `alt="path"`인 모드에서만 쓰인다(`heading="path"`와
  같은 규약, 01 §3.3). 고도 명령은 구간 선형 보간이고 소진 시 마지막 웨이포인트 고도로 정착한다
- 비행모드: **선언적 모드 테이블 + 실행기(sequencer)** (01 §3.3.1) — 각 모드 {진입조건, 활성
  명령, 이탈조건}. 발사→상승→순항→접근→플레어→미끄럼→정지
- 종방향 지령은 **고도·피치·강하율 중 하나**(배타, `validate_longitudinal`) — 셋 다 θ_cmd로
  가므로 우선순위 대신 구성 시점 거부다. 이탈 조건에
  `hdot_ge`/`hdot_le`·`on_ground`/`airborne`·`off_rail`이 있고, 뒤 셋은 항법에 없는 정보라 sim이
  ctx로 주입한다(없으면 **판정 불가**로 멈춘다 — False로 눙치면 모드가 조용히 선다)

  않는다** — `make_demo_fcl` → `law.init(dt)` → `law.runner`가 `flight/generate.py`와 같은
  경로이고, 그래서 응답이 커밋 산출물과 바이트 단위로 같다(테스트가 대조). 구성 오류는 엔진 판정
  → 422
- 게인 스케줄 자리(`GET /gains/catalog`, v0.27): 켤 수 있는 자리·현재 켜진 자리·**끄면 굳는 설계
  상수**·불가 사유·단위/설명을 18칸 격자로 회신하고, 켜지 않은 자리에도 제안 테이블(설계 상수 ×
  같은 동압 스케일)을 붙여 준다 — 체크하는 순간 곡선이 뜨고 설계점에서는 원래 상수와 같은 값에서
  출발한다. 목록을 서버가 다시 적지 않는다(M7 SCHEDULABLE) — 적으면 웹이 "켤 수 있다"고 보여 준
  자리가 실행 시점에 터진다. 기존 `GET /gains/demo`는 응답 형상 그대로 유지
- 레지스트리 검증(`POST /registry/{category}/{name}/validate`): 편집값을 엔진으로 실제 구성해
  범위·교차 조건까지 판정하고, 생성 코드가 명명할 파이썬 심볼(클래스·최단 임포트 경로)을
  인스턴스에서 회신 — 웹 코드 생성이 이름을 추론하지 않게 하는 원천 (02 v0.17)
- 영향성 1단(`POST /influence/structural`, 03-v0.19): 현재 편집 형상의 구조 + 도달성 한
  덩이(노드 212·간선 359·~70 ms라 동기). 요청 모델은 `codegen.py`의 `FlightCodeIn`을
  **상속**한다 — 같은 "현재 편집 형상"을 받는 자리라 필드와 유한성 검증을 다시 적으면 두 곳이
  갈라진다. **랭크(층 번호)는 보내지 않는다** — `refs`에서 전방 1회 주행이면 나오는 값이라
  서버와 화면이 각각 계산하면 같은 수를 두 곳에서 정의하게 된다. 도메인 판단은 전부 엔진 몫(구성
  오류→422)
- 후속: Δ리포트 API(M15 결선 — 영향성 1단으로 부분 해소, 2·3단 잔여), 검증 리포트(M12 구축 시),
  공력 DB 뷰어 API(DB 규격 확정 시), 파라미터 관리 계층(02 §5.5) 결선 — fingerprint 현재
  클라이언트 자기신고

## 6. 개발 순서 (Phase)

**[기본값]** 각 Phase는 검증 통과가 완료 기준. 같은 Phase 내 모듈은 병렬 개발 가능.

| Phase | 모듈 | 완료 기준 |
|---|---|---|
| 0 | common, params | `conventions.md` 확정, 변환·단위 단위테스트, 파라미터 스키마 규격, 인터페이스 계약 + 계보 지문 구현 |
| 1 | blocks ∥ tables ∥ env | 블록별 해석해 대조, 보간 정확도, ISA 표준값 대조 |
| 2 | plant ∥ nav | 물리검증(에너지 보존·수렴 차수), F-16 6DOF 재현 |
| 3 | trim → analysis ∥ pipeline | F-16 공개 트림·선형화 결과 재현 (verify 층1·2 완성), 산출물 DAG·무효화 동작 |
| 4 | fcl ∥ guidance → sim | 폐루프 시나리오 완주, 엔벨로프 감시 동작, 자사 기체 SCAS→AP→유도 순 설계, 파라미터 변경 Δ리포트 동작 |
| 5 | server → web | 사용자 워크플로우(02 §8) 1~12단계 전부 웹 수행 — **2~12단계 완료**; 1단계의 공력 DB 뷰어만 CFD DB 규격 [TBD] 대기 (06 §4) |

- verify(M12)는 Phase 2부터 각 단계에 걸쳐 지속 구축, Simulink 회귀(층3)는 폐쇄망 반입 시
- 설계 업무 관점 순서(트림→SCAS→AP→유도→비선형 검증, 01 §1)는 Phase 3~4 안에서 진행
