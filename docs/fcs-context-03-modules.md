# 컨텍스트 문서 3/3 — 모듈 분할 (소프트웨어 구조)

> 비행제어/유도법칙 설계툴 프로젝트의 **소프트웨어 모듈 분할** 컨텍스트.
> 도메인·설계 결정은 `fcs-context-01-control-law.md`, 구현 결정은 `fcs-context-02-implementation.md` 참조.
> 상태 표기: **[확정]** 결정 완료 / **[기본값]** 잠정 채택, 변경 가능 / **[TBD]** 미결

---

## 1. 분할 원칙

- **[확정]** 엔진 우선 (구현 문서 §2.3) — 모든 모듈은 Python API/CLI로 완결. server/web은 동일 API의 소비자일 뿐, 엔진 개발을 막지 않는다
- **[확정]** 모듈 = **독립 개발·독립 검증 단위**. 모듈 간 결합은 §4의 인터페이스 계약(데이터 구조)으로만 — 나중에 합치는 작업이 "인터페이스 맞추기"가 아니라 "이미 맞는 것 조립"이 되도록
- **[확정]** 계층 규칙: 상위 계층은 하위 계층만 의존. 같은 계층 간 상호 의존 금지. 조립(플랜트+법칙+항법 연결)은 sim 모듈이 담당 (composition root)
- **[확정]** **코어 경계 명시**: blocks·tables·env·plant + 법칙 실행부는 "코어"로 묶고 API를 고정 — 추후 C++(pybind11) 구현으로 교체 가능한 경계 (§7.1 언어 전략 참조)
- **[확정]** 교체 가능 컴포넌트(경로추종 알고리즘, 항법 모델, 적분기 등)는 레지스트리+파라미터 스키마 원칙(구현 문서 §2.3)을 따른다
- **[확정]** **설계값 연계·영향성 평가** (구현 문서 §2.4): 모든 산출물 계약은 자신이 계산된 파라미터 지문(lineage)을 보유하고, 산출물 의존 DAG(M15 pipeline)가 변경 전파·정량 Δ리포트·민감도 스윕을 담당한다

## 2. 계층 구조

```
[L5 인터페이스]   web ──────► server (FastAPI)
                                │  (엔진 Python API만 호출)
[L4 해석·실행]   trim │ analysis │ sim │ verify │ pipeline(영향성)
[L3 법칙]        fcl (SCAS·오토파일럿·믹싱·α리미터) │ guidance (경로·모드 실행기)
[L2 모델]        plant (6DOF·공력·추진·작동기·센서) │ nav (등가 오차 모델)
[L1 수치 코어]   blocks (제어 요소) │ tables (보간·공력DB) │ env (대기·지구)
[L0 기반]        common (규약·좌표·쿼터니언) │ params (파라미터·레지스트리·스키마)
```

### M0 `common` — 기반 규약
- 좌표계(동체축, NED)·단위계·부호 규약의 **코드 구현체**. `conventions.md`(도메인 문서 §6) 확정과 동시 작성 — 전 모듈이 이것만 참조
- 쿼터니언/DCM/오일러 변환, 좌표변환(NED↔동체↔WGS-84), 단위 변환 유틸
- 의존: 없음. 검증: 변환 왕복 일치, 참조값 대조 단위테스트

### M1 `params` — 파라미터 관리 + 레지스트리
- 단일 정의 원본(텍스트 파일, diff 가능)에서 게인·기하·질량/관성·리미터 값 관리. 단위·설명·유효범위 메타데이터 → UI 폼 자동 생성·입력 검증의 원천
- 연료 소모에 따른 질량·CG·관성 변화는 상태 의존 파라미터로 취급
- 컴포넌트 레지스트리: 교체 가능 컴포넌트의 등록·조회 + 파라미터 JSON 스키마 노출
- **[TBD]** 파일 포맷(YAML/JSON) — 웹 편집과 파일 편집이 같은 스키마 공유 (02§5.4)
- 의존: M0

### M2 `blocks` — 제어 요소 라이브러리
- 구현 문서 §2.2 전체 목록: Gain/Sum/Integrator(안티와인드업·초기화)/필터(Lag, Lead-Lag, Washout, Notch…)/PID(게인 스케줄 가능)/Saturation/Rate Limiter/Backlash/Fader 등
- 공통 프로토콜: `init(dt)` → `step(u) → y` → `reset(state)`. 이산화 계수는 주기로부터 자동 계산 (샘플레이트 파라미터화 원칙, 02§2.3)
- Simulink 사용 빈도 상위 기본 블록(Integrator, Sum, Gain, Saturation, Switch, Rate Limiter, Lookup, Unit Delay)이 **최우선 품질 목표** — 블록별 해석해/Simulink 참조값 대조 단위테스트
- 의존: M0, M1(스키마 등록)

### M3 `tables` — 보간·데이터
- 1D/2D/nD Lookup(보간·외삽 옵션), 공력 DB 로더(CSV/Excel→pandas→내부 포맷), 실속 경계 테이블(공력팀 정본), DB 유효범위 질의(엔벨로프 플래그의 근거), DB 뷰어용 슬라이스 추출(CL–α 곡선 등)
- **[TBD]** 보간 방식·외삽 정책·테이블 규격 (02§5.1, §5.3)
- 의존: M0

### M4 `env` — 환경 모델
- ISA 표준대기, 중력, WGS-84 지구모델. 바람/난류(Dryden)는 확장 항목
- 의존: M0. 검증: 표준대기표 대조

### M5 `plant` — 비행체 모델
- 서브패키지: `eom`(6DOF 운동방정식+적분기), `aero`(공력, M3 소비), `prop`(스로틀-추력 맵, 쌍발·차동추력), `mass`(연료 의존 질량·CG·관성), `actuator`(2차계 가정값 시작, rate/position limit·backlash), `sensor`(초기 이상센서 → 노이즈·지연)
- 서브패키지 단위로 독립 개발 가능 — 각각이 구현 문서 §3의 모듈 4·5·6
- 의존: M0, M1, M3, M4. 검증: 물리검증(에너지 보존, 스텝 반분 수렴 차수) + F-16 공개 모델
- **[기본값]** 1차 대상은 도메인 문서의 델타윙 고정익. 비행체 프로파일(공력DB+파라미터+법칙 템플릿) 교체로 타 기체 수용 (§7.2)

### M6 `nav` — 항법 등가 오차 모델
- 참값(plant) + 백색잡음 + 1차 마르코프 바이어스 + 지연 + 갱신주기 (02§3.1). EKF 미구현
- 레지스트리 등록 컴포넌트 — 추후 항법팀 실제 EKF/비행SW 코드로 교체 가능
- **핵심 계약: 법칙(M7·M8)은 절대 plant 참값을 직접 보지 않고 `NavOutput`만 소비** — 이 경계가 항법 강건성 평가를 가능케 함
- 의존: M0, M1, M2(잡음·지연 블록)

### M7 `fcl` — 비행제어법칙
- SCAS(피치/롤/요 PI, 러더 워시아웃), 오토파일럿(속도/고도/헤딩 PI, 차동추력 보상, 선회 시 엘리베이터/스로틀 피드포워드), 게인 스케줄(Mach·고도·연료 테이블), α 리미터(실속 경계 − 마진), 엘레본 믹싱[제어 할당](엘레본4 믹싱 행렬 + 러더 + 스로틀2)
- M2 블록의 조립으로 표현 — 파라미터·구조 분리 (추후 코드젠 모듈이 소비 가능한 구조, 02§1)
- 고정 아키텍처(01§3) — 자유 배선 없음. 멀티레이트 입력(항법 주기 ≠ 제어 주기) 전제
- 의존: M0~M4 (env는 스케줄 변수 마하 산출용 — L3→L1 계층 규칙 내). 검증: 선형모델 상 루프별 응답, 이후 폐루프 sim

### M8 `guidance` — 유도
- 웨이포인트 열 → 경로 생성 → 경로추종(알고리즘은 레지스트리 교체: LOS/L1/벡터필드 **[TBD]**), 출력은 속도/고도/헤딩 명령
- 비행모드: **선언적 모드 테이블 + 실행기(sequencer)** (01§3.3.1) — 각 모드 {진입조건, 활성 명령, 이탈조건}. 이륙→상승→…→착륙
- 범프리스 전환은 M2 Fader·적분기 초기화 인터페이스 소비
- 의존: M0~M2. (M7과 상호 의존 없음 — `GuidanceCommand` 계약으로만 연결)

### M9 `trim` — 트림·선형화
- scipy.optimize(SLSQP/trust-constr) 구속조건 트림, 수평정상비행부터. 케이스 매트릭스(컨디션×속도×고도×연료) 100+ 배치, 초기값 시드 전략(**[TBD]** 인접 케이스 시드 등)
- 수치섭동 선형화 → A/B/C/D + 트림점 메타. 종축/횡축 분리 추출
- 의존: M5 (plant를 함수로 소비). 검증: F-16 공개 트림·선형화 결과 재현 (verify 층1)

### M10 `analysis` — 안정성 해석
- python-control 기반: 고유치·감쇠비 + 모드 자동 분류(단주기/장주기/더치롤/롤/스파이럴), 이득·위상여유, 보드선도
- **마진 맵**: Mach-고도-연료 격자 전체 마진 계산·취약 구간 식별. 100 vs 50 Hz 이산화 영향 비교 자동화
- 의존: M2(이산 제어기 포함 해석), M9의 `LinearModel` 소비

### M11 `sim` — 시뮬레이션 프레임
- 멀티레이트 스케줄러: 플랜트 적분 주기(RK4) / 제어 주기(100→50 Hz) / 항법 갱신 주기 분리 (02§6)
- 조립(composition root): plant + nav + fcl + guidance를 §4 계약으로 연결. 시나리오(임무프로파일) 실행, 시계열 로깅
- **엔벨로프 감시(필수)**: α/β/Mach DB 이탈 플래그, 실속 마진(α_stall−α) 시계열, 임무 전체 최악 마진 요약 (02§6.1)
- 몬테카를로 배치(멀티프로세스) **[기본값]**
- 의존: M5~M8

### M12 `verify` — 검증·리포트
- 3층 검증(02§7): ① F-16 벤치마크 재현 ② 물리검증(에너지 보존·수렴 차수·미소섭동 선형 일치) ③ Simulink 회귀비교(결과 CSV 판독→허용오차 비교→리포트 자동 생성, 폐쇄망용)
- 검증 리포트 생성(합격기준표 포함). 각 단계 완료 기준의 실행 주체 — Phase 2부터 지속 구축
- 의존: M9~M11

### M15 `pipeline` — 설계 파이프라인·영향성 평가
- 산출물 의존 DAG 관리: params → 트림(M9) → 선형화(M9) → 마진(M10) → 시뮬(M11). 각 산출물은 계산 당시 ParamSet 지문(lineage)을 보유
- 파라미터 변경 시 영향받는 산출물만 자동 무효화·증분 재계산 (캐시)
- **정량 Δ리포트**: 변경 전/후 스냅샷 비교 — 트림 이동, 고유치·감쇠비·마진 변화, 응답지표·경로오차·실속마진 변화. 100 vs 50 Hz 비교(02§2.3)는 특수 사례
- 파라미터 스윕/민감도 스터디 (배치 실행 재사용)
- 의존: M1, M9~M11. 검증: 무효화 정확성(의존 그래프 단위테스트), Δ리포트 수치 회귀

### M13 `server` — 백엔드
- FastAPI: REST API, 배치 작업 실행(트림/시뮬), 웹소켓 진행률, 결과 저장. **엔진 Python API만 호출** — 도메인 로직 없음
- 단독 사용자·로컬 서버 (02§4). 의존: M1~M12, M15
- 구현됨(`server/claw_server`): 앱 팩토리+라우터(trim 배치/마진 맵/시뮬 실행/게인 조회/레지스트리 스키마·검증/작업/결과), 스레드 작업 실행기(엔진 on_progress 콜백 = 진행률+협조적 취소 단일 경로), JSON 결과 저장(본문/메타 분리·원자 쓰기·비유한값 정책), WS 진행률 푸시, 시뮬 재생 stride 다운샘플. 요청 검증은 엔진 소관(구성 ValueError/TypeError→422) + 경계 유한성만 서버가 차단
- 레지스트리 검증(`POST /registry/{category}/{name}/validate`): 편집값을 엔진으로 실제 구성해 범위·교차 조건까지 판정하고, 생성 코드가 명명할 파이썬 심볼(클래스·최단 임포트 경로)을 인스턴스에서 회신 — 웹 코드 생성이 이름을 추론하지 않게 하는 원천 (02 v0.17)
- 후속: Δ리포트 API(M15 결선), 검증 리포트(M12 구축 시), 공력 DB 뷰어 API(DB 규격 확정 시), 파라미터 관리 계층(02§5.5) 결선 — fingerprint 현재 클라이언트 자기신고

### M14 `web` — 프론트엔드
- **[확정]** 스택: 바닐라 ES 모듈 + no-build, 의존 0 (02 §4 — CSP·폐쇄망 현지 수정·반입 심사 근거). 서버 StaticFiles 정적 서빙 = 배포
- 트림 케이스 매트릭스 편집·진행률, 마진 맵/고유치/보드 대시보드, 지도 웨이포인트 편집(오프라인 타일/벡터 폴백), 시뮬 재생+엔벨로프 표시, 게인 테이블 편집, 스키마 기반 폼 자동 생성, DB 뷰어, 리포트
- 의존: M13 (HTTP만)
- 구현됨(`web/`): 워크플로우 2~5단계 + 6단계 열람 — 트림 매트릭스 편집(서펜타인 격자)·배치·판정 플래그 결과표, PM/GM 히트맵·고유치 맵·감쇠비 테이블, 게인 테이블 셀 편집→시뮬 주입, 모드 테이블·웨이포인트 편집(표 + NED 평면 캔버스 지도 — 클릭 추가·드래그 이동·우클릭 삭제·휠 줌/팬·▲▼ 재배열·궤적 오버레이, 오프라인 폴백 기본)→재생(시계열 모드 밴드·지상 궤적·시각 커서)+엔벨로프 요약, 산출물 목록·계보 열람, 코드 생성(편집 파라미터 반영 Python·C 헤더 + 변경 Δ·주의·추적성 표 — 블록별 및 전체 형상 스냅샷, 02 §1·v0.17). WS 진행률+취소 전 화면 공통. 로직은 js/lib(공존 테스트, node 내장 러너), 뷰는 DOM 조립 전용
- 후속: 스키마 기반 폼 자동 생성(레지스트리 스키마 API는 준비됨), 공력 DB 뷰어(DB 규격 [TBD] 대기), 보드선도(M10 데이터 API 후속), 검증 리포트 생성(M12 대기), 실지도 타일(폐쇄망 반입 검토 시)

## 4. 인터페이스 계약 (모듈 간 데이터 구조)

**[확정]** 모듈 결합은 아래 계약으로만. `common`에 정의, 버전 관리.

| 계약 | 생산자 → 소비자 | 내용 |
|---|---|---|
| `VehicleState` | plant → nav, sim | 위치(NED)·속도·쿼터니언·각속도·연료/질량 상태 (참값) |
| `NavOutput` | nav → fcl, guidance | VehicleState 동형 + 타임스탬프·유효 플래그 (오차 포함 출력) |
| `GuidanceCommand` | guidance → fcl | 속도/고도/헤딩 명령 + 축별 활성화 플래그 (모드가 정의) |
| `SurfaceCommand` | fcl → plant.actuator | 엘레본×4, 러더, 스로틀×2 명령 |
| `TrimCase` / `TrimResult` | (UI/파일) → trim → analysis | 비행조건 정의 / 트림 상태·입력·수렴 정보 + 자동 판정 플래그(도메인 문서 §4.1 — 잔차·포화·α 여유·연속성) |
| `LinearModel` | trim → analysis | A/B/C/D + 트림점 메타 + 종/횡축 분리 정보 |
| `SimResult` | sim → verify, server | 시계열 로그 + 엔벨로프 플래그·실속 마진 |
| `ParamSet` | params → 전 모듈 | 파라미터 스냅샷 (단위·범위 메타 포함) |
| `Block` 프로토콜 | blocks → fcl, nav | `init(dt)` / `step(u)→y` / `reset(state)` / `schema()` |
| Lineage (파라미터 지문) | params → 전 산출물 계약 | 산출물이 계산된 ParamSet의 fingerprint 문자열 + 입력 데이터(공력 DB·실속 경계 테이블) 해시·버전 — 무효화·영향성 평가(M15)·재현성의 키 |

## 6. 개발 순서 (Phase)

**[기본값]** 각 Phase는 검증 통과가 완료 기준. 같은 Phase 내 모듈은 병렬 개발 가능.

| Phase | 모듈 | 완료 기준 |
|---|---|---|
| 0 | common, params | `conventions.md` 확정, 변환·단위 단위테스트, 파라미터 스키마 규격, 인터페이스 계약 + 계보 지문 구현 |
| 1 | blocks ∥ tables ∥ env | 블록별 해석해 대조, 보간 정확도, ISA 표준값 대조 |
| 2 | plant ∥ nav | 물리검증(에너지 보존·수렴 차수), F-16 6DOF 재현 |
| 3 | trim → analysis ∥ pipeline | F-16 공개 트림·선형화 결과 재현 (verify 층1·2 완성), 산출물 DAG·무효화 동작 |
| 4 | fcl ∥ guidance → sim | 폐루프 시나리오 완주, 엔벨로프 감시 동작, 자사 기체 SCAS→AP→유도 순 설계, 파라미터 변경 Δ리포트 동작 |
| 5 | server → web | 사용자 워크플로우(02§8) 1~6단계 전부 웹 수행 — **2~5단계 + 6단계 열람 완료**; 1단계 DB 뷰어는 CFD DB 규격 [TBD]·6단계 리포트 생성은 M12 구축과 결부 (해당 대기 항목 해소 시 마감) |

- verify(M12)는 Phase 2부터 각 단계에 걸쳐 지속 구축, Simulink 회귀(층3)는 폐쇄망 반입 시
- 설계 업무 관점 순서(트림→SCAS→AP→유도→비선형 검증, 01§1)는 Phase 3~4 안에서 진행

## 7. 조율 결정 사항 (채택 완료)

### 7.1 언어 전략 — 구현 문서 §2.3과의 충돌

- **[확정 — 채택]** **Phase 1~4는 순수 Python 레퍼런스 구현**으로 진행하되, §1의 "코어 경계"(M2·M3·M4·M5 + 법칙 실행부) API를 고정. 성능이 문제 되는 시점(몬테카를로·배치)에 pybind11 C++ 구현을 드롭인 교체. Python판은 C++판의 **회귀 기준(oracle)** 으로 재사용 — 재작성 낭비가 아님
- → 구현 문서 §2.3 갱신 완료 (v0.8)
